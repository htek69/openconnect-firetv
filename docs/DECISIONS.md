# 意図的にそうしてある判断の記録（元に戻さないこと）

このドキュメントは、**「なぜそう実装したか」ではなく「なぜそうしなかったか」**の記録である。
どう実装したかはコードを読めば分かる。失われるのは外した選択肢とその理由だけなので、
それだけを集めてある。

対象は**将来誰かが善意で元に戻してしまいそうな判断**である。低すぎるように見える閾値、
バグのように見える非対称、直せそうに見える欠陥、揃えたくなる命名。いずれも一度は
検討して**そうしないと決めた**ものであり、戻すと壊れるものがある。

- 並び順は**戻されやすい順**である。番号は優先度であって履歴ではない。
- 各項目の「場所」の行番号はこのドキュメントを書いた時点（`0c8c2a5`）の値である。
  行が動いていたら関数名で探すこと。
- 理由がすでに KDoc に書いてある項目は、ここでは**要点と索引だけ**にしてある。
  実際に変更する前に、指した KDoc を読むこと。

関連: 仕様書 [docs/superpowers/specs/2026-09-27-throughput-failover-design.md](superpowers/specs/2026-09-27-throughput-failover-design.md)（速度低下による切替の設計と**既知の誤判定の一覧**）、
実機での確認状況 [docs/MANUAL-TEST.md](MANUAL-TEST.md)。

## 1. 送信側の閾値 `demandTxKbps = 5` を引き上げない

**決めたこと。** 「遅い」の判定に使う送信側の条件を 5 kbps に据え置く（裁定R22）。
待機中の雑多な通信で誤判定することは承知のうえである。

**なぜ。** 引き上げる案を外した。送信側の条件は「誰かが使おうとしている」ことの代用に
過ぎない（仕様書 4-2）。そして**この機能が対象にしている遅い候補では、送信の大半が
受信への ACK であり受信速度に比例して下がる。** 仕様書 2-1 で受信 424 kbps を実測した
候補なら送信は概算 8〜20 kbps にしかならず、閾値を 5 から上げると、**この機能が
対象にしているまさにその候補で条件が成立しなくなる。**

**元に戻すと。** 機能が誤検知しなくなる代わりに、**本来検知すべき候補でも発火しなく
なる**（＝機能が無いのと同じになる）。据え置いた側の代償は仕様書 §6-4 に記録済みで、
Fire TV の待機中の通信が 5 kbps を超えると何も再生していないのに切り替わりうる。
これは実機確認の項目でもある（`docs/MANUAL-TEST.md` 10-5。**最も起きやすい誤判定**
として、放置は60秒ではなく5分以上行うことになっている）。

**場所。** `SlowLinkDetector.kt:10`（`SlowLinkThresholds.demandTxKbps` の既定値）、
判定は同 `:125`（`isSlow`）。設定画面には出していない（仕様書 5: 利用者が調整して
意味のある値ではない）。

## 2. 速度起因の切替には人の入力を守る門があり、死活起因の切替には無い

**決めたこと。** `onSlowLinkSwitch` は `awaitingHumanAuthInput()` を見て切替を止めるが、
プローブ連続失敗による切替（`onProbeResult`）は**見ない。この非対称は意図的である。**

**なぜ。** 両方に同じ門を付ける案を外した。遅さは**誤りうる判断**であり、仕様書 §6 が
その誤判定を5つ列挙している——だから人が答えられるあいだは待つ。対してプローブの連続
失敗は**トンネルがもう無い証拠**である。消えたトンネルに向かってパスワードを打たせ
続けても、その入力はサーバへ届かない。次候補で認証をやり直すほうが良い。

**元に戻すと。** 死活起因の切替にも門を付けると、**もう存在しないトンネルの前で認証
ダイアログを開いたまま待つ**状態が作れる。Ruling 22 が存在する理由そのものを失う。

**なぜ記録が要るか。** この非対称は利用者の目には「入力中にダイアログが消える」という、
**裁定93/94 で直した不具合とまったく同じ見え方**をする。実装を知らない側には区別が
つかないので、報告を受けた人が善意でこれを「直す」危険が最も高い。
`docs/MANUAL-TEST.md` 節11 の項目14 にも**期待された動作**として明記してある。

**場所。** 門は `FailoverController.kt:1275`（`onSlowLinkSwitch`）。判定そのものは
同 `:1484`（`awaitingHumanAuthInput`）で、**その KDoc の末尾（`:1469` から）に理由が
全部書いてある**ので、変える前にそこを読むこと。門を持たない側は同 `:970`
（`onProbeResult`）。機械生成側の対応する例外は
`FailoverControllerInvariantTest` の I3 の `deadTunnelEvidence`（`:560`）。

## 3. 「人が居るか」「その指示がまだ生きているか」を時計で判定しない

**決めたこと。** 人の在席と指示の生存を、**観測**（認証ダイアログの描画先が bind されて
いるか／publish された状態が動いたか）だけで判定する。時計は使わない（裁定78）。

**なぜ。** 時間しきい値による解決を外した。この問いに時計で答えると、**打つのが遅い
利用者を切ってしまう**だけである。時間の側に正解は無い（リモコンでパスワードを打つのに
45秒でも足りないことがある）。**この2週間で2回、時計による解決が入りかけて外して
いる**: 印を60秒で取り下げる仕組み（`FIRST_LOGIN_STALL_MS`。削除した）と、それを
残したまま発火条件を足して人の入力窓に当たらないようにする案（採らなかった）。
正しい解決は**指示が捨てられることを実行の前に観測可能にする**ことだった
（`HomeRows.firstLoginRefusal` → `HomeScreen` の既存の `statusMessage`。新しい通知
経路は作っていない）。

**誤読しないこと。** 時計による**締切**は存在する（接続タイムアウト45秒、無人プロンプト
10秒、枯渇後のバックオフ）。禁じているのはそれらではなく、**「人が居るか」の答えを
時計から取ること**である。実際、その2つの締切はどちらも人の在席の観測で門を張って
あり（`awaitingHumanAuthInput` / `dialogHostAttachedProvider`）、時計が人の入力窓に
当たらないようにしてある。

**元に戻すと。** リモコンで打つのが遅い利用者の認証が途中で切られる。同じ誤りを3度
繰り返すことになる。

**場所。** `FailoverController.kt:1433`（`awaitingHumanAuthInput` の KDoc「この状態が
無限に続かない根拠」——**有界性の根拠は時間ではなく「人が居る」という観測そのもの**
であることの証明）、`HomeRows.kt:568`、`HomeScreen.kt:488`（削除した60秒の経緯）。

**番号についての注意。** コード内の「裁定78」は**2つの無関係な件**を指している。
ひとつはここで扱っている「生存性の判定に時計を使わない」
（`FailoverController.kt:1434` / `HomeRows.kt:610` / `HomeScreen.kt:415`, `:490`）。
もうひとつは**長押しで消費された `ACTION_UP` の判定基準**で、こちらは裁定80 で
差し替え済みである（`LongPressKeyUpFilter.kt:4-11` / `TvMainActivity.kt:83-86` /
`HomeScreen.kt:768`）。番号だけを頼りに引くと別の話に行き着くので、
**前後の文を読んでどちらの件かを確かめること。**

## 4. 「初回ログイン中」の表示が残る残件を塞がない（据え置き）

**決めたこと。** 「初回ログイン」を実行したあと `context.startService(...)` が例外を
投げ、それが残り全部の候補で起き、かつ実行前の状態がちょうど `Exhausted(G, 0)` だった
場合、状態の鍵が動かないため画面は失敗を観測できず、行は「初回ログイン中」と表示された
まま残る（画面を離れれば消える）。**直さないと決めた。**

**なぜ。** 塞ぐ手は2つしかない。(a) 時計を持ち込む——項目3 が禁じている。(b) dispatch の
結果を画面へ返す新しい経路を足す——実装計画が禁じている。**どちらの禁止もこの欠陥より
先に決まっており、稀な場面の見た目の嘘のために覆さない。** API 25 にはバックグラウンド
起動制限が無いので `startService` が投げるのは実質 OOM のときだけである。**データは
失われず、二重にダイヤルもしない。**

**元に戻すと（＝特例を1つ足すと）。** 同じ形の特例をこれまで何度も潰してきており、
潰すたびに別の特例が現れている。将来これを本当に直すなら、**画面が dispatch の結果を
状態から推測するのをやめる**こと（＝計画の制約を変える判断が要る）。`FailoverState.Idle`
が識別情報を持たない `data object` であることがこの限界の根っこである。

**場所。** `HomeRows.kt:598`（`firstLoginAttemptProgress` の KDoc「据え置いた残件」。
**この項目の全文はそこにある**）。`docs/MANUAL-TEST.md` 節11 の項目12 にも記載。

## 5. 「遅い」は窓全体で均した平均で判定する（裁定R20）— 厳しい規則へ戻さない

**決めたこと。** 窓（既定60秒）の最古と最新の累計バイト数の差を、その2点の経過時間で
割った平均を閾値に当てる。

**なぜ。** 以前の「5秒ごとの小区間が全部閾値を下回ること」を外した。その規則では一度
でも上振れすると数え直しになり、**ばらつく遅い回線——まさにこの機能が対象にしている
候補——で永久に成立しない**恐れがあった。動画クライアントは区間ごとにまとめて取りに
来るので、小区間は必ず上下する。仕様書 4-2 の「窓で均した値」を字義どおり実装した
ほうが正しい。

**代償を承知のうえである。** 感度が上がった結果、**仕様書 §6-1（低ビットレート再生の
誤判定）が縁の事例ではなく主要な誤判定経路になった。** 小区間ごとの規則が偶然この
誤判定を抑えていたぶんが失われ、接続先の速度に関わらずストリームのビットレートが
`slowRxKbps` を下回っていれば約60秒で必ず発火する。既定 OFF はこのためである。

**元に戻すと。** この誤判定は減るが、**対象の候補で発火しなくなる**恐れが戻る。戻す
なら仕様書 §6-1 を読み直してからにすること。なお実機で発火を確認できていない
（`docs/MANUAL-TEST.md` 10-3 が唯一の確認手段であり、未実施である）。

**場所。** `SlowLinkDetector` のクラス KDoc（裁定R20 の段は `SlowLinkDetector.kt:24`〜）と
`isSlow`（同 `:97`）。判定が真になる3条件（窓が埋まっている／証拠が新しい／平均が
両条件を満たす）もそこにある。

## 6. 一周の予算はメンバー数を数えている（起動できる候補数ではない）

**決めたこと。** 速度起因の切替の上限は「**グループのメンバー数** - 1 回」である。初回
ログイン待ちや安全策 S1 で除外された候補も数に入るので、k 件が飛ばされる構成では予算は
k ぶん過剰に配分される。**これは意図どおりで、直さない。**

**なぜ。** 起動できる候補の件数で数え直す案を外した。それをやると毎ティック
`needsFirstLoginProvider` を引くことになり、「供給関数を引くのは候補選択のときだけ」
という約束（裁定16 のメインスレッド規律）と衝突する。**そして過剰でも暴走しない**:
切替を実際に止めているのは予算ではなく `onSlowLinkSwitch` の
`nextStartableIndex(...) == null` の門であり、こちらは参照のたびに引き直すので、
起動できる候補を使い切った時点で必ず先に止まる。予算は常に**余る側**（安全側）に外れ、
足りなくなることは原理的に無い。**その門は折り返さないので、最後のメンバーに
繋がっているあいだは予算が残っていても発火しない**（項目14）。

**元に戻すと。** 予算の側を「正確」にしても振る舞いは改善せず、毎ティックの供給関数
呼び出しをメインスレッドに持ち込む。オフバイワンのバグに見えるが、バグではない。

**場所。** `FailoverController.kt:1323`（`slowLinkLapAvailable`。KDoc は統合レビューの
所見2 を受けて訂正済みで、**過剰であることを明記してある**）。機械生成側は
`FailoverControllerInvariantTest` の I5。

## 7. 保存キー `slow_link_settings_v1` に `failover_` 接頭辞を付けない

**決めたこと。** 他の5つのキーは `failover_*_v1` だが、このキーだけ接頭辞が無い。
**不揃いだが変えない。**

**なぜ。** 命名を揃える案を外した。キーは**永続化される値**であり、後から変えると
既存の端末に入っている設定を読めなくする。揃えるには移行処理が必要になり、見た目の
一貫性のために移行コードとその分の不具合の余地を抱えることになる。

**元に戻すと（＝揃えると）。** 移行を書かずに改名すれば、利用者が保存した
「速度低下で切り替える」の設定が黙って既定値（OFF）に戻る。設定画面が壊れたようにしか
見えず、原因も分からない。

**場所。** `GroupStore.kt:207`（`KEY_SLOW_LINK`）。他の5つは同 `:202`〜`:206`。
このキーは `isReloadTriggerKey`（同 `:194`）にも入っている——外すと設定画面での保存が
動作中の `FailoverService` に届かない。

## 8. 初回ログインの判定は `FORMDATA-` だけを見る（値は読まない）

**決めたこと。** そのプロファイル自身の prefs に `FORMDATA-` で始まるキーが1つも無い
ことを「初回ログイン未完了」とする。**キー名の有無だけを見て、値は1つも読まない。**

**なぜ。** `ACCEPTED-CERT-` も見る案を外した。証明書の承認は証明書のハッシュを受け
入れた記録に過ぎず、**認証フォームに答えた証拠にはならない**（承認だけ済んで初回
ログインが未完了という状態は実際に起こりうる）。裁定67 の「アドレス変更時に消すべき
キー」の判定が2接頭辞を見るのは別の意味であり、そちらは変えていない。
また、個数にも依存しない（フォームの構成で変わる）。

**承知している副作用。** 「パスワードを保存しない」を選んだ利用者は空文字の
`FORMDATA-` キーを持つので「保存済み」と見なされる。それは利用者自身の選択であり、
その後の認証失敗は既存の安全策 S1（認証段階に到達して通らなかった候補の除外）が扱う。

**元に戻すと。** `ACCEPTED-CERT-` を判定に含めると、証明書だけ承認済みで認証情報を
持たない接続先が「ログイン済み」と誤判定され、無人の巡回でその候補を起動してしまう
（＝この門番が存在する理由を失う）。

**実機での裏取り。** 端末上の9プロファイルについて `FORMDATA-` で始まるキーの**個数
だけ**を数えた（値は読んでいない）。症状が出ていた1件が **0 件**、他の8件はいずれも
**3 件**。判定基準は実機で完全に分離していた。

**場所。** `ProfileRepository.kt:416`（`hasSavedFormData`。`SharedPreferences` に触れない
純関数として切り出してある）。呼び出しは同 `:434`（`needsFirstLogin`）。
裁定67 の別判定は同 `:390`（`isCredentialOrCertKey`）。

## 9. `nextStartableIndex` は `Int?` を返す（`Int` ではない）

**決めたこと。** 「起動できる候補が無い」を `null` で表す。

**なぜ。** 枯渇を `group.memberUuids.size` で返す形を捨てた。速度起因の切替の門は
「無い」と「添字 0」の区別に依存しており、`size` を返す形では呼び出し側が取り違えうる。
`null` なら取り違えようがない。

**元に戻すと。** 取り違えた切替は `startCandidateFrom` で候補を見つけられず
`enterExhausted` に落ち、**繋がってはいた（ただ遅い）トンネルをバックオフのあいだ
失う。** 遅いままの接続より悪い結果であり、この機能の目的にも反する。

**場所。** `FailoverController.kt:747`（`nextStartableIndex`。飛ばす規則をこの1か所に
集めてあることの理由も KDoc にある）。門は同 `:1281`。

## 10. 速度起因の切替は `unattended = true` で候補を探す

**決めたこと。** 速度低下による切替が次候補を探すときは無人として引く。よって初回
ログインが未了のメンバーは「起動できる候補」に数えない。

**なぜ。** 速度低下による切替は**エンジン自身の判断**であり利用者の操作ではないので、
人が居なければ成功しえない接続先を選んではならない。それを防ぐことが初回ログインの
門番の目的である。数えてしまうと、門を通り抜けた切替が `startCandidateFrom`
（そちらも `unattended = true`）でその候補を飛ばし、結局 `enterExhausted` に落ちて
項目9 の事故を起こす。加えて、無人で起動できない候補へ移そうとすること自体が
裁定93/94 の「利用者の認証ダイアログを消さない」に反する。

**元に戻すと。** 遅いだけで生きていたトンネルを失い、そのうえ誰も答えられない認証
ダイアログの前で止まる。

**場所。** `FailoverController.kt:1281`（`onSlowLinkSwitch` 内の
`nextStartableIndex(group, s.candidateIndex + 1, unattended = true)`）。
テストは `FailoverControllerSlowLinkTest` の
`初回ログインが未了のメンバーしか残っていなければ遅くても切り替えない`。

## 11. 切替理由の寿命は「その切替が作った接続が生きているあいだ」

**決めたこと。** 「速度低下で切替」の表示は、`Idle` / `Exhausted` に着地した時点で
消す。**完了した切替の理由も、その接続が終われば消える。**

**なぜ。** 残す案を外した。残すと、切断後に点灯して `AutoConnectGroup` が**先頭候補から**
繋ぎ直したあとの行にもその理由が出てしまい、**今のセッションでは起きていない切替を
説明する。** 「理由が無い」より「間違った理由が表示される」方が悪い（裁定R19）。
理由が正しかった場面で寿命が短くなる向きだが、この向きを選ぶ。

**あわせて: 判定の `when` に `else` を書かないこと。** 消す条件は状態の種類で言い切って
ある（前進した先は `Connecting` だけであり、前進しなかった5経路はすべて `Idle` か
`Exhausted` に着地する）。網羅にしてあるのは、`FailoverState` にケースが増えたときに
**この判断をやり直させる**ためである。`else` を足すと、新しい状態が黙ってどちらかの側に
分類される。

**元に戻すと。** 経路ごとの特例で消していく形に戻り、経路が増えるたびに同じ誤表示が
戻る（実際にそうなっていた）。

**場所。** `FailoverStateHolder.kt:191`（`onFailoverStateChanged`。**5経路の列挙と
「条件は切替が前進したかであり、状態の種類の列挙ではない」の議論が KDoc にある**）。
同じ作法の `when` は `HomeRows.firstLoginRecheckKey`（`HomeRows.kt:492`）と
`FailoverController.withCandidateIndex`（`:411`）。

## 12. kbps の計算に相殺する `× 1000 / ÷ 1000` を書き足さない

**決めたこと。** `dRx * 8 / spanMs` と書く。以前の
`dRx * 8 * 1000 / spanMs / 1000` には戻さない。

**なぜ。** 非負の整数では両者は**厳密に等しい**（証明は KDoc にある）。等しいのに
`* 1000` は中間結果を1000倍するので、**桁あふれまでの余裕を3桁ぶん捨てていた。**

**元に戻すと。** あふれの境が `Long.MAX_VALUE / 8`（≒1.15EB）から
`Long.MAX_VALUE / 8000`（≒1.15PB）へ下がる。境を越えると積が回り込み、受信・送信の
速度が無意味な値になって誤検知と取りこぼしの両方を作る。

**場所。** `SlowLinkDetector.kt:112`（証明付きのコメント）。等価であることは
`SlowLinkDetectorPropertyTest` の **P9**（`:181`）が旧式と新式をあふれない域の全入力で
突き合わせて押さえており、**境そのものは同 `:264` の
`桁あふれの境の記録 これを超えるデルタでは演算が厳密でなくなる`** が記録している
（`BigInteger` と突き合わせて、境の内側では厳密・1つ外では回り込むことを固定）。

## 14. 速度起因の切替は折り返さない（最後のメンバーでは発火しない）

**決めたこと。** `onSlowLinkSwitch` は行き先を
`nextStartableIndex(group, s.candidateIndex + 1, unattended = true)` で探し、
`nextStartableIndex` は `fromIndex` からメンバー列の末尾までしか見ない。**先頭へ
折り返さない。** したがって **グループの最後のメンバーに繋がっているあいだ、速度起因の
切替は一度も起きない。** 一周の予算（項目6）がいくら残っていても関係しない。

**なぜ。** 折り返す案を外した。折り返すと「一周したら止める」（仕様書 4-5）の意味が
予算の数え方だけに依存することになり、止め方が1つになる。いまは**止め方が2つあり、
どちらも時計を使わない**——行き先が無い（この門）と、予算を使い切った（項目6）。
前者は参照のたびに最新の除外集合と供給関数で引き直されるので、後者より確実に効く。

**気づきにくい帰結（ここが記録の理由）。** 速度起因**以外**の経路——死活判定による
切替、枯渇後の再試行——は普通に添字を進める。その結果 **エンジンが最後のメンバーまで
流れ着くと、速度起因の切替はそこで黙って無効になる。** 画面には何も出ない。利用者から
見ると「設定を ON にしたのに何も起きない」であり、**設定が壊れているように見える。**
解除されるのは利用者の明示的な接続（`onUserConnect` が添字0から始める）か、
死活判定で別の候補へ移ったときだけである。

**元に戻すと（＝折り返すようにすると）。** 止め方が予算だけになる。予算はメンバー数を
数えており（項目6）飛ばされた候補のぶん過剰なので、**遅いと誤判定したまま候補の間を
余分に行き来する**余地が広がる。仕様書 §6 が誤判定を列挙しているとおり、速度の判定は
誤りうる。

**実機確認への影響。** `docs/MANUAL-TEST.md` 節 10-3 を行うときは、**繋がっている候補が
グループの最後のメンバーでないこと**を先に確かめること。2026-10-08 の試行は、この門と
安全策 S1 の除外集合という2つの前提を確かめずに走らせたため、**切り替わらなかったという
記録しか得られず、判定を下せなかった**（節 10 の観測記録に残してある）。

**場所。** `FailoverController.kt:1281`（門）と `FailoverController.kt:752`
（`nextStartableIndex` の `while (index < group.memberUuids.size)`）。項目6 の
「実際に切替を止めているのはこの門」という記述と対になる。

**2026-10-08 追記。** この門は不発の原因では**なかった**（候補は添字1 で最後では
なかった）。原因は別で、ログを入れて特定した——**`ProcNetDevThroughputSource` が
測るインターフェース名を `tun0` に固定していること**である（下の項目15）。
**切替の機構そのものは実機で動くことを確認した**（窓が埋まった直後に判定が出て、
候補が 1→2→3→4 と進んだ）。経緯は `docs/MANUAL-TEST.md` 節 10-3 にある。

## 15. 測るインターフェース名を `tun0` に固定してはいけない（**2026-10-08 に実機で露呈**）

**事実。** `ProcNetDevThroughputSource` は `iface: String = "tun0"` を既定にしていて、
`FailoverService` はその既定のまま使っている。**これは実機で壊れる。**

**なぜ壊れるか。** Android は VPN を張り直すたびに新しい `tun` 番号を割り当て、
**古いものは `DOWN` のまま `/proc/net/dev` に残る。** 実機で `ip link` を見ると
`tun0` / `tun1` / `tun3` が `DOWN`、`tun4` だけが `UP` という状態になっていた。
10秒間で動いていたのは `tun4` だけ（受信 +3606 / 送信 +2053）で、`tun0` は
1 バイトも動かない。

**その結果。** 差分が常に 0 になるので送信側の条件（`txKbps > demandTxKbps`）で
落ち、`slowLinkProvider()` が false に固定され、**速度起因の切替は二度と起きない。**
画面には何も出ないので、利用者からは「設定を ON にしたのに何も起きない」に見える。

**最も厄介な性質: 切替そのものが新しい `tun` を作るので、数回切り替わると
この機能は自分で自分を壊す。** 一度も切り替わらないうちは `tun0` のままなので
動き、動いた結果として動かなくなる。だから**短い確認では通ってしまう。**

**単体テストが届かない理由。** `parseProcNetDev` の性質テストは「与えられた文字列
から**指定した名前**の行を正しく取り出す」ことを押さえている。**「どの名前を
指定すべきか」はテストの外側**にあり、JVM のテストからは見えない。項目13 が
記録した「手書きが届かない組み合わせ」の教訓が、もう一段外側で再現した。

**直すときの選択肢（未実施。設計の判断が要る）**

- `ConnectivityManager` から VPN の `Network` を引き、`LinkProperties.interfaceName`
  を使う。**Android が「いまの VPN はどれか」を知っているので推測が入らない。**
  ただし `FailoverService`（Android 側）に閉じること——`SlowLinkDetector` と
  `FailoverController` は Android に依存しない（項目3 の周辺の約束）
- `/sys/class/net/*/operstate` で `UP` の `tun*` を選ぶ。procfs だけで済むが、
  複数が `UP` のときの決め方を決める必要がある
- 既存 Java（`OpenVpnService`）が持っている名前を使う。**「既存 Java を変更
  しない」という制約に触れる**ので、触れずに取り出せるかを先に確かめること

**どれを選んでも、`ThroughputSource` が「測れなかった」を null で返す約束
（`sampleThroughput` の `?.let` が唯一の関門）は変えないこと。**
「測れない」を「遅い」と解釈してはならない、という性質がこの機能の安全側である。

**場所。** `ProcNetDevThroughputSource.kt:26` と `FailoverService.kt` の
`throughputSource = ProcNetDevThroughputSource()`。
