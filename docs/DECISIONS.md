# 意図的にそうしてある判断の記録（元に戻さないこと）

このドキュメントは、**「なぜそう実装したか」ではなく「なぜそうしなかったか」**の記録である。
どう実装したかはコードを読めば分かる。失われるのは外した選択肢とその理由だけなので、
それだけを集めてある。

対象は**将来誰かが善意で元に戻してしまいそうな判断**である。低すぎるように見える閾値、
バグのように見える非対称、直せそうに見える欠陥、揃えたくなる命名。いずれも一度は
検討して**そうしないと決めた**ものであり、戻すと壊れるものがある。

- 並び順は**戻されやすい順**である。番号は優先度であって履歴ではない。
- 各項目の「場所」の行番号はこのドキュメントを書いた時点（`0c8c2a5`）の値である。
  行が動いていたら関数名で探すこと。
- 理由がすでに KDoc に書いてある項目は、ここでは**要点と索引だけ**にしてある。
  実際に変更する前に、指した KDoc を読むこと。

関連: 仕様書 [docs/superpowers/specs/2026-09-27-throughput-failover-design.md](superpowers/specs/2026-09-27-throughput-failover-design.md)（速度低下による切替の設計と**既知の誤判定の一覧**）、
実機での確認状況 [docs/MANUAL-TEST.md](MANUAL-TEST.md)。

**2026-10-09: 速度起因の切替の判定は、受信・送信の速度から、疎通確認の応答時間とそのばらつきへ
改められた**（[改訂版仕様](superpowers/specs/2026-10-09-path-quality-failover-design.md)）。
項目1〜17 のうち判定の中身に触れる記述（送信の閾値、窓の平均、`tun` の取り違えが作った
症状など）は**旧判定についての記録**で、各項目に改訂後の扱いを追記してある。
項目18〜23 は改訂の過程で決めたものである。**改訂後の判定は実機で一度も確認して
いない**——「直した」と「動くと確かめた」を混同しないこと（項目15、項目17）。

## 1. 送信側の閾値 `demandTxKbps = 5` を引き上げない

**決めたこと。** 「遅い」の判定に使う送信側の条件を 5 kbps に据え置く（裁定R22）。
待機中の雑多な通信で誤判定することは承知のうえである。

**なぜ。** 引き上げる案を外した。送信側の条件は「誰かが使おうとしている」ことの代用に
過ぎない（仕様書 4-2）。そして**この機能が対象にしている遅い候補では、送信の大半が
受信への ACK であり受信速度に比例して下がる。** 仕様書 2-1 で受信 424 kbps を実測した
候補なら送信は概算 8〜20 kbps にしかならず、閾値を 5 から上げると、**この機能が
対象にしているまさにその候補で条件が成立しなくなる。**

**元に戻すと。** 機能が誤検知しなくなる代わりに、**本来検知すべき候補でも発火しなく
なる**（＝機能が無いのと同じになる）。据え置いた側の代償は仕様書 §6-4 に記録済みで、
Fire TV の待機中の通信が 5 kbps を超えると何も再生していないのに切り替わりうる。
**2026-10-09 追記: その誤判定が実機で起きた。** 7分半の待機中に、端末自身の
バックグラウンド通信（最大 6.3 Mbps）の前後で**受信 5 kbps・送信 86〜97 kbps**
という窓が4つ成立し、候補を添字1 から添字5 まで歩き切った
（`docs/MANUAL-TEST.md` 節 10-5-1）。**閾値を上げても直らない**——観測された
送信は 86〜97 kbps で、5 を 50 に上げても成立する。**この項目の「上げてはならない」
は依然正しいが、上げないことで安全になるわけでもない。**
問題は閾値の値ではなく、**送信を「誰かが使おうとしている」の代用にしている
こと自体**である（下の項目17）。

これは実機確認の項目でもある（`docs/MANUAL-TEST.md` 10-5。**最も起きやすい誤判定**
として、放置は60秒ではなく5分以上行うことになっている）。

**2026-10-09 改訂追記: この条件自体が改訂で消えた。** 経路品質の改訂
（[改訂版仕様](superpowers/specs/2026-10-09-path-quality-failover-design.md) §2）は、
判定から送信側の条件（`demandTxKbps`）を**削除**し、代わりに受信に下限
（`rxFloorKbps`、既定 50 kbps）を置いた。したがって「5 を上げるか据え置くか」という
上の問いは、改訂後の判定には存在しない。

**それでもこの項目は消さない。** 経緯を消すと、将来また「送信速度を需要の代用にする」
案が出る。上の議論は**その案に解が無いことの記録**である——送信の閾値は、上げれば
対象の候補（424 kbps）で発火せず、上げなくても上り主体の通信（86〜97 kbps）で
誤発火する。**両側から挟まれている。** 改訂版が送信の条件を捨てたのはこのためで、
同じ軸を別の値で復活させる案は、この項目と項目17 を読んでから検討すること。

**「条件が消えた」は「改訂後の判定が正しい」を意味しない。** 改訂後の判定は
**実機で一度も確認していない**（`docs/MANUAL-TEST.md` 節 10 の新しい手順はすべて
未実施）。

**場所。** `SlowLinkDetector.kt:10`（`SlowLinkThresholds.demandTxKbps` の既定値）、
判定は同 `:125`（`isSlow`）。設定画面には出していない（仕様書 5: 利用者が調整して
意味のある値ではない）。**改訂後もこの2つはコードに残っている**が、製品の判定
（`PathQualityDetector.isDegraded`）はどちらも使わない（受信の窓の平均だけを
`SlowLinkDetector.windowAverage` から借りる）。残っているのは、
受信の窓として `SlowLinkDetector` を使い回しており（`PathQualityDetector` の `rx`）、
その既存の試験（項目13 の性質テスト群を含む）を無改変で通しているためである。
**残っているコードを根拠に、送信の条件が今も効いていると読まないこと。**

## 2. 速度起因の切替には人の入力を守る門があり、死活起因の切替には無い

**決めたこと。** `onSlowLinkSwitch` は `awaitingHumanAuthInput()` を見て切替を止めるが、
プローブ連続失敗による切替（`onProbeResult`）は**見ない。この非対称は意図的である。**

**なぜ。** 両方に同じ門を付ける案を外した。遅さは**誤りうる判断**であり、仕様書 §6 が
その誤判定を5つ列挙している——だから人が答えられるあいだは待つ。対してプローブの連続
失敗は**トンネルがもう無い証拠**である。消えたトンネルに向かってパスワードを打たせ
続けても、その入力はサーバへ届かない。次候補で認証をやり直すほうが良い。

**元に戻すと。** 死活起因の切替にも門を付けると、**もう存在しないトンネルの前で認証
ダイアログを開いたまま待つ**状態が作れる。Ruling 22 が存在する理由そのものを失う。

**なぜ記録が要るか。** この非対称は利用者の目には「入力中にダイアログが消える」という、
**裁定93/94 で直した不具合とまったく同じ見え方**をする。実装を知らない側には区別が
つかないので、報告を受けた人が善意でこれを「直す」危険が最も高い。
`docs/MANUAL-TEST.md` 節11 の項目14 にも**期待された動作**として明記してある。

**場所。** 門は `FailoverController.kt:1275`（`onSlowLinkSwitch`）。判定そのものは
同 `:1484`（`awaitingHumanAuthInput`）で、**その KDoc の末尾（`:1469` から）に理由が
全部書いてある**ので、変える前にそこを読むこと。門を持たない側は同 `:970`
（`onProbeResult`）。機械生成側の対応する例外は
`FailoverControllerInvariantTest` の I3 の `deadTunnelEvidence`（`:560`）。

## 3. 「人が居るか」「その指示がまだ生きているか」を時計で判定しない

**決めたこと。** 人の在席と指示の生存を、**観測**（認証ダイアログの描画先が bind されて
いるか／publish された状態が動いたか）だけで判定する。時計は使わない（裁定78）。

**なぜ。** 時間しきい値による解決を外した。この問いに時計で答えると、**打つのが遅い
利用者を切ってしまう**だけである。時間の側に正解は無い（リモコンでパスワードを打つのに
45秒でも足りないことがある）。**この2週間で2回、時計による解決が入りかけて外して
いる**: 印を60秒で取り下げる仕組み（`FIRST_LOGIN_STALL_MS`。削除した）と、それを
残したまま発火条件を足して人の入力窓に当たらないようにする案（採らなかった）。
正しい解決は**指示が捨てられることを実行の前に観測可能にする**ことだった
（`HomeRows.firstLoginRefusal` → `HomeScreen` の既存の `statusMessage`。新しい通知
経路は作っていない）。

**誤読しないこと。** 時計による**締切**は存在する（接続タイムアウト45秒、無人プロンプト
10秒、枯渇後のバックオフ）。禁じているのはそれらではなく、**「人が居るか」の答えを
時計から取ること**である。実際、その2つの締切はどちらも人の在席の観測で門を張って
あり（`awaitingHumanAuthInput` / `dialogHostAttachedProvider`）、時計が人の入力窓に
当たらないようにしてある。**2026-10-09 に足した「一周したあとの再開」の時計
（`rearmAfterLapMin`）も、禁じられた側に当たらない**——理由は項目23。

**元に戻すと。** リモコンで打つのが遅い利用者の認証が途中で切られる。同じ誤りを3度
繰り返すことになる。

**場所。** `FailoverController.kt:1433`（`awaitingHumanAuthInput` の KDoc「この状態が
無限に続かない根拠」——**有界性の根拠は時間ではなく「人が居る」という観測そのもの**
であることの証明）、`HomeRows.kt:568`、`HomeScreen.kt:488`（削除した60秒の経緯）。

**番号についての注意。** コード内の「裁定78」は**2つの無関係な件**を指している。
ひとつはここで扱っている「生存性の判定に時計を使わない」
（`FailoverController.kt:1434` / `HomeRows.kt:610` / `HomeScreen.kt:415`, `:490`）。
もうひとつは**長押しで消費された `ACTION_UP` の判定基準**で、こちらは裁定80 で
差し替え済みである（`LongPressKeyUpFilter.kt:4-11` / `TvMainActivity.kt:83-86` /
`HomeScreen.kt:768`）。番号だけを頼りに引くと別の話に行き着くので、
**前後の文を読んでどちらの件かを確かめること。**

## 4. 「初回ログイン中」の表示が残る残件を塞がない（据え置き）

**決めたこと。** 「初回ログイン」を実行したあと `context.startService(...)` が例外を
投げ、それが残り全部の候補で起き、かつ実行前の状態がちょうど `Exhausted(G, 0)` だった
場合、状態の鍵が動かないため画面は失敗を観測できず、行は「初回ログイン中」と表示された
まま残る（画面を離れれば消える）。**直さないと決めた。**

**なぜ。** 塞ぐ手は2つしかない。(a) 時計を持ち込む——項目3 が禁じている。(b) dispatch の
結果を画面へ返す新しい経路を足す——実装計画が禁じている。**どちらの禁止もこの欠陥より
先に決まっており、稀な場面の見た目の嘘のために覆さない。** API 25 にはバックグラウンド
起動制限が無いので `startService` が投げるのは実質 OOM のときだけである。**データは
失われず、二重にダイヤルもしない。**

**元に戻すと（＝特例を1つ足すと）。** 同じ形の特例をこれまで何度も潰してきており、
潰すたびに別の特例が現れている。将来これを本当に直すなら、**画面が dispatch の結果を
状態から推測するのをやめる**こと（＝計画の制約を変える判断が要る）。`FailoverState.Idle`
が識別情報を持たない `data object` であることがこの限界の根っこである。

**場所。** `HomeRows.kt:598`（`firstLoginAttemptProgress` の KDoc「据え置いた残件」。
**この項目の全文はそこにある**）。`docs/MANUAL-TEST.md` 節11 の項目12 にも記載。

## 5. 「遅い」は窓全体で均した平均で判定する（裁定R20）— 厳しい規則へ戻さない

**決めたこと。** 窓（既定60秒）の最古と最新の累計バイト数の差を、その2点の経過時間で
割った平均を閾値に当てる。

**なぜ。** 以前の「5秒ごとの小区間が全部閾値を下回ること」を外した。その規則では一度
でも上振れすると数え直しになり、**ばらつく遅い回線——まさにこの機能が対象にしている
候補——で永久に成立しない**恐れがあった。動画クライアントは区間ごとにまとめて取りに
来るので、小区間は必ず上下する。仕様書 4-2 の「窓で均した値」を字義どおり実装した
ほうが正しい。

**代償を承知のうえである。** 感度が上がった結果、**仕様書 §6-1（低ビットレート再生の
誤判定）が縁の事例ではなく主要な誤判定経路になった。** 小区間ごとの規則が偶然この
誤判定を抑えていたぶんが失われ、接続先の速度に関わらずストリームのビットレートが
`slowRxKbps` を下回っていれば約60秒で必ず発火する。既定 OFF はこのためである。

**元に戻すと。** この誤判定は減るが、**対象の候補で発火しなくなる**恐れが戻る。戻す
なら仕様書 §6-1 を読み直してからにすること。なお実機で発火を確認できていない
（`docs/MANUAL-TEST.md` 10-3 が唯一の確認手段であり、未実施である）。

**2026-10-09 改訂追記: 上の「約60秒で必ず発火する」「実機で発火を確認できていない」は
旧判定の記述である。** 2026-10-09 に旧判定は実機で発火し（10-3-2）、同日に待機中の
誤判定も起きた（10-5-1）。改訂後の判定では、受信の平均は**帯の条件のひとつ**にすぎず、
**応答時間とそのばらつきの両方が基準を超えない限り発火しない**
（`PathQualityDetector.isDegraded`）。したがって「ストリームのビットレートが
`slowRxKbps` を下回っていれば必ず発火する」は、改訂後は成り立たない（仕様書 §3 の
表の1行目）。**ただし「成り立たない」は設計と JVM のテストが言っていることであり、
実機では確認していない。**

窓の平均で判定するという**この項目の決定そのもの（裁定R20）は、受信側の窓として
今も生きている**——`PathQualityDetector` は受信の窓に `SlowLinkDetector` を使い回して
いる。元に戻すと何が壊れるかの議論は、受信の窓についてそのまま当てはまる。

**場所。** `SlowLinkDetector` のクラス KDoc（裁定R20 の段は `SlowLinkDetector.kt:24`〜）と
`isSlow`（同 `:97`）。判定が真になる3条件（窓が埋まっている／証拠が新しい／平均が
両条件を満たす）もそこにある。

## 6. 一周の予算はメンバー数を数えている（起動できる候補数ではない）

**決めたこと。** 速度起因の切替の上限は「**グループのメンバー数** - 1 回」である。初回
ログイン待ちや安全策 S1 で除外された候補も数に入るので、k 件が飛ばされる構成では予算は
k ぶん過剰に配分される。**これは意図どおりで、直さない。**

**なぜ。** 起動できる候補の件数で数え直す案を外した。それをやると毎ティック
`needsFirstLoginProvider` を引くことになり、「供給関数を引くのは候補選択のときだけ」
という約束（裁定16 のメインスレッド規律）と衝突する。**そして過剰でも暴走しない**:
切替を実際に止めているのは予算ではなく `onSlowLinkSwitch` の
`nextStartableIndex(...) == null` の門であり、こちらは参照のたびに引き直すので、
起動できる候補を使い切った時点で必ず先に止まる。予算は常に**余る側**（安全側）に外れ、
足りなくなることは原理的に無い。**その門は折り返さないので、最後のメンバーに
繋がっているあいだは予算が残っていても発火しない**（項目14）。

**元に戻すと。** 予算の側を「正確」にしても振る舞いは改善せず、毎ティックの供給関数
呼び出しをメインスレッドに持ち込む。オフバイワンのバグに見えるが、バグではない。

**場所。** `FailoverController.kt:1323`（`slowLinkLapAvailable`。KDoc は統合レビューの
所見2 を受けて訂正済みで、**過剰であることを明記してある**）。機械生成側は
`FailoverControllerInvariantTest` の I5。

## 7. 保存キー `slow_link_settings_v1` に `failover_` 接頭辞を付けない

**決めたこと。** 他の5つのキーは `failover_*_v1` だが、このキーだけ接頭辞が無い。
**不揃いだが変えない。**

**なぜ。** 命名を揃える案を外した。キーは**永続化される値**であり、後から変えると
既存の端末に入っている設定を読めなくする。揃えるには移行処理が必要になり、見た目の
一貫性のために移行コードとその分の不具合の余地を抱えることになる。

**元に戻すと（＝揃えると）。** 移行を書かずに改名すれば、利用者が保存した
「速度低下で切り替える」の設定が黙って既定値（OFF）に戻る。設定画面が壊れたようにしか
見えず、原因も分からない。

**2026-10-09 改訂追記: この理由は改訂でそのまま使われた。** 経路品質の改訂で、設定画面の
ラベルは「速度低下で切り替える」から「経路品質の低下で切り替える」に変わり、項目も
増減した（`demandTxKbps` は消え、4つ増えた）が、**キーは `slow_link_settings_v1` の
まま据え置いた。** 新しい項目は `SlowLinkSettings` の既定値で補い、消えた項目は
`ignoreUnknownKeys` が読み飛ばす。**ラベルを変えたことをキーの改名の根拠にしないこと**
——ラベルは表示で、キーは永続化された値である。

**場所。** `GroupStore.kt:207`（`KEY_SLOW_LINK`）。他の5つは同 `:202`〜`:206`。
このキーは `isReloadTriggerKey`（同 `:194`）にも入っている——外すと設定画面での保存が
動作中の `FailoverService` に届かない。

## 8. 初回ログインの判定は `FORMDATA-` だけを見る（値は読まない）

**決めたこと。** そのプロファイル自身の prefs に `FORMDATA-` で始まるキーが1つも無い
ことを「初回ログイン未完了」とする。**キー名の有無だけを見て、値は1つも読まない。**

**なぜ。** `ACCEPTED-CERT-` も見る案を外した。証明書の承認は証明書のハッシュを受け
入れた記録に過ぎず、**認証フォームに答えた証拠にはならない**（承認だけ済んで初回
ログインが未完了という状態は実際に起こりうる）。裁定67 の「アドレス変更時に消すべき
キー」の判定が2接頭辞を見るのは別の意味であり、そちらは変えていない。
また、個数にも依存しない（フォームの構成で変わる）。

**承知している副作用。** 「パスワードを保存しない」を選んだ利用者は空文字の
`FORMDATA-` キーを持つので「保存済み」と見なされる。それは利用者自身の選択であり、
その後の認証失敗は既存の安全策 S1（認証段階に到達して通らなかった候補の除外）が扱う。

**元に戻すと。** `ACCEPTED-CERT-` を判定に含めると、証明書だけ承認済みで認証情報を
持たない接続先が「ログイン済み」と誤判定され、無人の巡回でその候補を起動してしまう

## 10. 速度起因の切替は `unattended = true` で候補を探す

**決めたこと。** 速度低下による切替が次候補を探すときは無人として引く。よって初回

## 11. 切替理由の寿命は「その切替が作った接続が生きているあいだ」

**決めたこと。** 「速度低下で切替」の表示は、`Idle` / `Exhausted` に着地した時点で
消す。**完了した切替の理由も、その接続が終われば消える。**

**なぜ。** 残す案を外した。残すと、切断後に点灯して `AutoConnectGroup` が**先頭候補から**
繋ぎ直したあとの行にもその理由が出てしまい、**今のセッションでは起きていない切替を
説明する。** 「理由が無い」より「間違った理由が表示される」方が悪い（裁定R19）。
理由が正しかった場面で寿命が短くなる向きだが、この向きを選ぶ。

**あわせて: 判定の `when` に `else` を書かないこと。** 消す条件は状態の種類で言い切って
ある（前進した先は `Connecting` だけであり、前進しなかった5経路はすべて `Idle` か
`Exhausted` に着地する）。網羅にしてあるのは、`FailoverState` にケースが増えたときに
**この判断をやり直させる**ためである。`else` を足すと、新しい状態が黙ってどちらかの側に
分類される。

**元に戻すと。** 経路ごとの特例で消していく形に戻り、経路が増えるたびに同じ誤表示が
戻る（実際にそうなっていた）。

**2026-10-09 追記: 表示される文字列を「経路品質で切替」に改めた**
（`HomeRows.SLOW_LINK_SWITCH_REASON`）。判定の根拠が受信速度から経路品質へ移ったのに
ホームの行だけ「速度低下で切替」と出し続けており、設定画面のラベル
（「経路品質の低下で切り替える」）と**画面ごとに違う呼び方**になっていた。
文言の変更は表示だけの話で、この項目が決めた**寿命**には触れていない。
`MANUAL-TEST.md` の旧判定の記録（10-3-2 など）は**当時の文字列のまま**残してある。

**ただし「前へ進んだ切替」と「一周の終わりに最良へ戻った切替」は、この文字列では
区別していない**（`returnToBest` も `bySlowLink = true` で `failOver` に入るため）。
区別するには `FailoverState.FailingOver` に情報を足すことになり、不変条件の試験一式が
この状態の形に依存している。枝の最後にそれを動かす代償の方が大きいと判断した。
**実機で切替の列を追うときは、接続先の名前の変化で読むこと**（前進は順方向に進み、
戻りは最良の候補へ跳ぶ）。`MANUAL-TEST.md` 節10 の新しい手順はそう書いてある。

**場所。** `FailoverStateHolder.kt:191`（`onFailoverStateChanged`。**5経路の列挙と
「条件は切替が前進したかであり、状態の種類の列挙ではない」の議論が KDoc にある**）。
同じ作法の `when` は `HomeRows.firstLoginRecheckKey`（`HomeRows.kt:492`）と
`FailoverController.withCandidateIndex`（`:411`）。

## 14. 速度起因の切替は折り返さない（最後のメンバーでは発火しない）

**決めたこと。** `onSlowLinkSwitch` は行き先を
`nextStartableIndex(group, s.candidateIndex + 1, unattended = true)` で探し、
`nextStartableIndex` は `fromIndex` からメンバー列の末尾までしか見ない。**先頭へ
折り返さない。** したがって **グループの最後のメンバーに繋がっているあいだ、速度起因の
切替は一度も起きない。** 一周の予算（項目6）がいくら残っていても関係しない。

**なぜ。** 折り返す案を外した。折り返すと「一周したら止める」（仕様書 4-5）の意味が
予算の数え方だけに依存することになり、止め方が1つになる。いまは**止め方が2つあり、
どちらも時計を使わない**——行き先が無い（この門）と、予算を使い切った（項目6）。
前者は参照のたびに最新の除外集合と供給関数で引き直されるので、後者より確実に効く。

**気づきにくい帰結（ここが記録の理由）。** 速度起因**以外**の経路——死活判定による
切替、枯渇後の再試行——は普通に添字を進める。その結果 **エンジンが最後のメンバーまで
流れ着くと、速度起因の切替はそこで黙って無効になる。** 画面には何も出ない。利用者から
見ると「設定を ON にしたのに何も起きない」であり、**設定が壊れているように見える。**
解除されるのは利用者の明示的な接続（`onUserConnect` が添字0から始める）か、
死活判定で別の候補へ移ったときだけである。

**元に戻すと（＝折り返すようにすると）。** 止め方が予算だけになる。予算はメンバー数を
数えており（項目6）飛ばされた候補のぶん過剰なので、**遅いと誤判定したまま候補の間を
余分に行き来する**余地が広がる。仕様書 §6 が誤判定を列挙しているとおり、速度の判定は
誤りうる。

**2026-10-09 改訂追記: 「最後のメンバーでは発火しない」は、前へ進む切替についての
記述になった。** 経路品質の改訂（仕様書 §2-A）で、一周の終わりに**応答時間が最良だった
候補へ戻す切替**が加わった。最後のメンバーに繋がっていて判定が真のとき、
`onSlowLinkSwitch` は前へ進まず `returnToBest` に入り、**その一周で前へ進む切替が
一度でも起きていれば**（`lap.switches() > 0`。`FailoverController.kt:1418`）、
最良の候補が別にあれば**一周に一度だけ後ろへ戻る。**
**前進が0回の一周では何も起きない**——比較する相手が無いからである（項目22 に詳しい）。 折り返して前へ進む切替が起きないこと自体は変わらない
（上の「元に戻すと」は前へ進む折り返しについて、今も当てはまる）。戻る切替の扱いは
項目22。**「最後のメンバーで何も起きない」を、改訂後の挙動として読まないこと**
——ただし戻る切替は実機で一度も観測していない（`docs/MANUAL-TEST.md` 節 10 の N-4）。

**実機確認への影響。** `docs/MANUAL-TEST.md` 節 10-3 を行うときは、**繋がっている候補が
グループの最後のメンバーでないこと**を先に確かめること。2026-10-08 の試行は、この門と
安全策 S1 の除外集合という2つの前提を確かめずに走らせたため、**切り替わらなかったという
記録しか得られず、判定を下せなかった**（節 10 の観測記録に残してある）。

**場所。** `FailoverController.kt:1281`（門）と `FailoverController.kt:752`
（`nextStartableIndex` の `while (index < group.memberUuids.size)`）。項目6 の

## 15. 測るインターフェース名を `tun0` に固定してはいけない（**2026-10-08 に実機で露呈**）

**事実。** `ProcNetDevThroughputSource` は `iface: String = "tun0"` を既定にしていて、
`FailoverService` はその既定のまま使っている。**これは実機で壊れる。**

**なぜ壊れるか。** Android は VPN を張り直すたびに新しい `tun` 番号を割り当て、
**古いものは `DOWN` のまま `/proc/net/dev` に残る。** 実機で `ip link` を見ると
`tun0` / `tun1` / `tun3` が `DOWN`、`tun4` だけが `UP` という状態になっていた。
10秒間で動いていたのは `tun4` だけ（受信 +3606 / 送信 +2053）で、`tun0` は
1 バイトも動かない。

**その結果。** 差分が常に 0 になるので送信側の条件（`txKbps > demandTxKbps`）で
落ち、`slowLinkProvider()` が false に固定され、**速度起因の切替は二度と起きない。**
画面には何も出ないので、利用者からは「設定を ON にしたのに何も起きない」に見える。

**最も厄介な性質: 切替そのものが新しい `tun` を作るので、数回切り替わると
この機能は自分で自分を壊す。** 一度も切り替わらないうちは `tun0` のままなので
動き、動いた結果として動かなくなる。だから**短い確認では通ってしまう。**

**単体テストが届かない理由。** `parseProcNetDev` の性質テストは「与えられた文字列
から**指定した名前**の行を正しく取り出す」ことを押さえている。**「どの名前を
指定すべきか」はテストの外側**にあり、JVM のテストからは見えない。項目13 が
記録した「手書きが届かない組み合わせ」の教訓が、もう一段外側で再現した。

**直した（`394d706`）。** 1つめの案を採った。

- 新しい port `VpnInterfaceNameSource`。実装 `ConnectivityVpnInterfaceName` が
  `ConnectivityManager` から `TRANSPORT_VPN` のネットワークを引き、
  `LinkProperties.interfaceName` を取る
- 判定規則は純関数 `selectVpnInterfaceName` に切り出した（Android 非依存、
  テスト8件）。**名前が2つ以上あるときは曖昧なので null**——片方を選ぶと
  「利用者が見ているのとは別のトンネル」を根拠に切り替えうる
- `ProcNetDevThroughputSource` は供給関数を受け取る形にし、**既定値を置かない**。
  省略できると同じ欠陥が戻るので、「どれを測るか」を決めずに使うことを
  コンパイル時に不可能にした
- `FailoverService` は毎ティック名前を解決し、**変わったら窓を捨てる**。
  別のインターフェースの累計値を同じ窓に混ぜると差分が2つのカウンタの差に
  なって速度が跳ねる。`syncSlowLinkCandidate` は候補の入れ替わりしか見て
  いないので、同じ候補へ繋ぎ直して名前だけ変わる場合を捕まえない

**2026-10-09 に実機で確認した。** ただし**この修正だけでは動かなかった**——
猶予の記録にもう1つ欠陥があり（下の項目16）、2件は互いを隠していた。
両方を直して 10-3 と 10-6 が通った（`docs/MANUAL-TEST.md` 節 10-3-2）。

**2026-10-09 改訂追記: 改訂後の判定もこの修正に乗っている。** 経路品質の判定は受信の
帯（下限〜上限）を条件に持ち、その受信速度は同じ `/proc/net/dev` の読み取りから
出る。測るインターフェースを取り違えると受信が 0 に張り付き、下限が 0 でないかぎり
帯の条件で落ちる——つまり**取り違えの症状（「ON にしたのに何も起きない」）は改訂後も
同じ形で出る**。上の「その結果」の `txKbps > demandTxKbps` は旧判定の記述である。

**検討して外した選択肢**

- `ConnectivityManager` から VPN の `Network` を引き、`LinkProperties.interfaceName`
  を使う。**Android が「いまの VPN はどれか」を知っているので推測が入らない。**
  ただし `FailoverService`（Android 側）に閉じること——`SlowLinkDetector` と
  `FailoverController` は Android に依存しない（項目3 の周辺の約束）
- `/sys/class/net/*/operstate` で `UP` の `tun*` を選ぶ。procfs だけで済むが、
  複数が `UP` のときの決め方を決める必要がある
- 既存 Java（`OpenVpnService`）が持っている名前を使う。**「既存 Java を変更
  しない」という制約に触れる**ので、触れずに取り出せるかを先に確かめること

**どれを選んでも、`ThroughputSource` が「測れなかった」を null で返す約束
（`sampleThroughput` の `?.let` が唯一の関門）は変えないこと。**
「測れない」を「遅い」と解釈してはならない、という性質がこの機能の安全側である。

**場所。** `ProcNetDevThroughputSource.kt:26` と `FailoverService.kt` の
`throughputSource = ProcNetDevThroughputSource()`。

## 16. 接続直後の猶予は「最初の `Connected`」だけで記録する（**2026-10-09 に実機で露呈**）

**事実。** `onVpnStateChanged` の

```kotlin
if (core == VpnCoreState.Connected && candidateConnectedAtMs == null) {
```

の **`== null` を外してはいけない。** 外すと速度低下による切替が二度と起きない。

**なぜ。** **既存コアは `Connected` を一度ではなく繰り返し通知する。**
`OpenVpnService.setStats()` が `wakeUpActivity()` を呼び、それが現在の状態を
再アナウンスし、`onStatsUpdate` は OpenConnect ライブラリが**通信中に定期的に**
呼ぶ。毎回書き換えると「トンネルが張れた時刻」が常に「いま」になり、
`graceAfterConnectSec` の猶予が**永久に経過しない。**

実機の診断ログでは `clock.nowMs() - candidateConnectedAtMs` が常に **9ms 前後**で、
判定が `SLOW` を出していても `onSlowLinkSwitch` の門が **143 回連続**で
`within-grace` で止まっていた。

**最も重要な性質: この欠陥はこの機能を自分の発火条件の下で不可能にしていた。**
判定には送信側の通信（`demandTxKbps`）が必要で、**その通信そのものが猶予を
押し戻す。** 通信が無ければ猶予は進むが、そのときは判定が成立しない。

**2026-10-09 改訂追記: 「判定には送信側の通信が必要で、その通信が猶予を押し戻した」は
旧判定の自己妨害の記述である。** 改訂後の判定は送信を使わないので、この形の自己妨害は
無い。**それでも `== null` は外してはならない**——外すと `Connected` の再通知のたびに

外すと機能が黙って死ぬ、という性質はこの項目の理由のまま生きている。

**項目15 との関係（両方直さないと動かない）。** 2026-10-08 に一度だけ発火したのは、
項目15 の欠陥で**死んだインターフェースを測っており通信が無かった**ため猶予が
進めた、という偶然の組み合わせである。**2件は互いを隠していた**——片方だけ直しても

**既存のテストがすり抜けた理由。** `FailoverControllerSlowLinkTest` も

**場所。** `FailoverController.kt` の `onVpnStateChanged`（`candidateConnectedAtMs`
への代入）。候補ごとに測り直すのは `startCandidateFrom` が null に戻すことで

## 17. 送信速度は「人が使おうとしている」の代用になっていない（**2026-10-09 に実機で露呈。判定の根拠を変えたが、実機での確認は未了**）

**事実。** 仕様書 4-2 は送信速度（`demandTxKbps`）を「誰かがこの回線を使おうと
している」の代用に使っている。**実機ではこの代用が成り立たなかった。**

2026-10-09 の待機中の観測（`docs/MANUAL-TEST.md` 節 10-5-1）では、誰も何も
見ていない7分半のあいだに **受信 5 kbps・送信 86〜97 kbps** の60秒窓が4つ成立し、
速度起因の切替が候補を添字1 から添字5 まで歩き切った。

**なぜ代用が崩れるか。** 送信が太いのは**上りのバックグラウンド通信**（端末の
テレメトリ、アップロード、同期）でも起きる。そのとき受信が細いのは
**「回線が遅い」からではなく「何も落としていないから」**である。
判定の2条件がどちらも成立してしまう。

**閾値では直らない。** 項目1 が記録しているとおり `demandTxKbps` を上げると
仕様書 2-1 の 424 kbps の候補で発火しなくなる。かつ観測された送信は 86〜97 kbps
なので、上げても誤判定は残る。**両側から挟まれていて、この軸に解は無い。**

**考えられる方向（どれも未実施。設計の判断が要る）**

- **受信の「要求」を見る。** 送信ではなく「受信しようとしているのに来ていない」
  ことを示す証拠（再送、RTT の悪化、ウィンドウの詰まり）を使う。ただし
  `/proc/net/dev` のバイト数だけでは取れないので、測る対象を変える話になる
- **上りと下りの比を見る。** 受信が細く送信が太いのは**上り主体の通信**であり、
  「遅い回線で下りが詰まっている」とは形が違う。比で弾けるかは要検証
- **人が見ているかを別の根拠で見る。** 画面が点いているか、前面のアプリが何かを
  再生しているか。**ただし裁定78 と項目3 の「人が居るかを時計で判定しない」の
  精神に照らすと、画面の点灯も弱い代用である**（点けたまま離席する）
- **この機能を既定 OFF の実験機能として据え置く。** ← **2026-10-09 に利用者が
  これを選んだ。** 上の3案はいずれも仕様の見直しを伴い、どれが正しいかを机上で
  決められない。実機で誤判定が出ることが分かっている以上、**動かないものを
  動くふりで同梱しない**のが先である

**決めたこと（2026-10-09、利用者の判断）: 実験機能として据え置く。**

- 既定は **OFF**。コードは残すが、**ON で常用できる状態ではない**

  （`SettingsScreen.kt`）。**この文言を弱めないこと**——以前は低ビットレート
  再生だけを警告していたが、実測されたのは「何も見ていないときにも切り替わる」

- `README.md` の「仕組み」にも同じ警告を置いた

  据え置くのは速度起因の切替だけである

**再開するときの入口。** 項目17 の「考えられる方向」から選び直すこと。

**場所。** `SlowLinkDetector.isSlow()` の `txKbps > thresholds.demandTxKbps`、

### 2026-10-09 改訂: 判定の根拠を応答時間へ変えた（**実機での確認は未了**）

**何を変えたか。** 利用者に4案が示され、**応答時間を主にする案**が選ばれた
（仕様書 §8）。設計は
[改訂版仕様](superpowers/specs/2026-10-09-path-quality-failover-design.md)。要点:

- 判定は、プローブの**接続の所要時間の中央値**が `degradedRttMs`（既定 250 ms）を
  超え、**最大と最小の差**が `degradedJitterMs`（既定 150 ms）を超え、かつ窓の平均の
  受信速度が `rxFloorKbps`（既定 50）と `slowRxKbps`（既定 1000）の**帯の内側**に
  あるときに成立する。**応答時間の2条件が本体で、受信は帯の条件にすぎない。**
  送信速度は使わない（項目1）
- 根拠: 受信速度は `min(回線の容量, 誰かが要求している量)` で、**受動観測はこの2つを
  分離できない**（仕様書 §1）。応答時間は需要に依存しないので、「回線が本当に悪い」
  と「回線は良いが誰も落としていない」を分けられる。上の方向1の「RTT の悪化」に近いが、
  再送やウィンドウの詰まりは見ておらず、**既存の死活プローブの接続時間**を使う
- 追加の宛先も権限も要らない。ただし**プローブの1周期あたりの接続が最大5回になり、
  それはこの機能が OFF のときも同じ**である（項目18）

**これは「直した」であって「動くと確かめた」ではない。**（項目15 と同じ規律: 直した修正が実機で動くまで「直った」と書かない）

- 確認したのは JVM のユニットテストだけである。2026-10-09 の誤判定の入力（受信 5 /
  送信 86 kbps で経路が健全）と、旧仕様 §2-2 の実測値（素の回線 73.5 ms / mdev 5.0、
  遅い候補 137〜379 ms / mdev 140〜336）を入力に固定してある。**それは判定の論理が
  その入力で正しく振る舞うことの確認であり、実機の TCP 接続時間がその入力のように
  分布することの確認ではない。**
- **実機では、新しい判定を一度も走らせていない。** 待機中に切り替わらないこと
  （この改訂の合否を決める項目）も、遅い経路で切り替わることも、速い経路で切り
  替わらないことも、一周のあとで最良へ戻ることも、すべて未確認である。手順は
  `docs/MANUAL-TEST.md` 節 10 の N-1〜N-8 で、**すべて未実施**
- 設定画面の警告（【実験機能】）は「変えたあとの動作はまだ実機で確認できていません」と
  書いている。**実機で確かめたら差し替えるのはその一文であり、「遅延とビットレートは
  別物…」の文は確認後も残す**（下の限界3）

**確認が済んでも消えない限界（仕様書 §3。ここに書くのは、ここで利用者と保守者が出会う
ため）。**

1. **遅延は良いのに帯域だけ細い回線は、見えない。** 帯域制限やシェーピングを受けた経路は
   応答時間が健全なまま容量だけが低い。受動観測では測れない（必要なのは能動的な測定で、
   旧仕様の「追加の通信は行わない」と衝突する。改訂版も採っていない）
2. **既定の `degradedRttMs = 250` は万人向けではない。** 応答時間にはプローブの宛先までの
   距離が乗る。宛先から遠い利用者では、経路が健全でも常時超えうる。ばらつきの条件が
   同時に要るのでそれだけでは発火しないが、**既定値が万人向けでないことは事実**で、
   だから4項目を利用者が変えられる
3. **応答時間が悪い経路でも、利用者が見ているものは問題なく見えていることがある。**
   遅延とビットレートは別物で、**切り替える判断が実際の見え方と一致しない場合がある**
   （旧仕様から変わらない。設定画面の警告にも書いてある）

**外した案について。** 仕様書 §8 は「外した案と理由はこの項目にある」と書くが、この項目が
記録している理由は上の「考えられる方向」の中身までである（送信の閾値で解けないこと、
画面の点灯は弱い代用であること）。**4案を示した対話そのものは文書に残っていない。**
将来、外した方向を採り直すときは、上の各方向を新しい前提で検討し直すこと。

**再開の入口（改訂版）。** 実機で新しい判定が誤判定したら、上の「コードの欠陥は

## 18. 試行回数を増やすと「1回でも成功すれば到達可能」の意味が変わる（**2026-10-09、実装中に発見。実機では未確認**）

**事実。** `TcpHealthProbe.probeTimed` は1周期に接続を最大5回行うが、**到達可否
（`ProbeOutcome.reachable`）は1回目の試行の結果そのもの**である。「5回のうち1回でも
成功すれば到達可能」にしてはならない。1回目が失敗した周期は、残りの試行を**行わない**。

**何が信じられていたか。** 改訂版仕様の初稿は「1回でも成功すれば到達可能。これは現在と
同じ強さ」と書いていた。応答時間のサンプルを増やすために接続を複数回にするのは
自然で、到達可否を「どれか成功」にするのはそれに見合った素直な定義に見える。

**実際はどうだったか。** 既存の `probe()` は接続を**1回**しか行わない
（`TcpHealthProbe.probe` は `attemptOnce` をそのまま返す）。「1回でも成功すれば可」が
現在と同義だったのは、**試行が1回だったから**である。試行が5回になると、同じ文が
現在よりはるかに寛容な意味になる。

| 接続が失敗する割合 | 3周期連続で失敗と数えられる確率（既定の `failureThreshold = 3`） |
|---|---|
| 8割 | 改訂前 ≒ **0.51** → 「どれか成功」にすると ≒ **0.035**（周期の失敗確率 0.8^5 ≒ 0.33 の3乗） |
| 5割 | 改訂前 **0.125** → 「どれか成功」にすると ≒ **0.00003**（周期の失敗確率 0.5^5 の3乗） |

つまり**最も切り替えたい状況——経路が半分壊れている——で、`failureThreshold` に
到達しなくなる。** 既存の死活による切替が、この機能を足したことで事実上働かなくなる。
**新しい機能が、既存の機能を、最も必要な状況で壊す**形である。しかもプローブは、この
機能が**OFF のときも**5回接続するので、既定のまま使っている利用者にも及ぶ。

**どう見つかったか。** 実装の過程で「死んだ経路では tick が最大25秒止まる」という懸念
（`probeIntervalSec` は最小10秒なので、5回×5秒が周期に収まらない）を検算していて、
その計算のために `probe()` の原典を読み、1回しか試していないことに気づいた。
**仕様書の「現在と同じ強さ」は、原典と突き合わせずに書かれた断言だった。**
仕様書は `ffa94e5` で直した。型もテストもこれを教えない——「どれか成功」の実装は
型検査を通り、複数回化のテストも通る。

**直し方。** 到達可否は1回目で決める。これで失敗回数の数え方（`failureThreshold`）も、
周期の意味も、改訂前と**厳密に同じ**になる。1回目が失敗した周期が残りを行わないのは、
到達可否がもう決まっていて、死活の切替へ向かっている経路の応答時間を測る意味が
無いからで、副産物として1周期の最悪所要時間が `probeTimeoutMs` 1回ぶんに戻り、
最小の周期（10秒）にも収まる。1回目が成功した周期は、残りを**合計 `probeTimeoutMs` × 2
の壁時計予算**の範囲で走らせ、**払えない試行は始めない**（次の試行を始める条件は
`経過 + probeTimeoutMs <= 予算`）。各回のタイムアウトを残り予算に切り詰めて記録する案は
採らなかった——実際には5秒以上かかる経路を2秒の遅延として記録することになり、
測定が嘘になる。

**代償（承知のうえである）。**

- **サンプルを取り逃す。** 1回目が失敗した周期は応答時間が1個しか残らず、遅い経路では
  予算のため1周期のサンプルが5より少なくなる（既定: 予算10秒・各回上限5秒）。
  **正確な数は各回の所要時間で決まる**——門は `elapsed + timeoutMs <= budget` なので、
  1回目が即座に返れば3回、各回が上限近くかかれば**2回**で打ち切られる。減る方向は
  **判定を偽にする側（切り替えない側）**なので、誤った切替は生まない。
- **この機能が OFF でも、疎通確認の1周期の接続が最大5本になる。** `PROBE_ATTEMPTS` は
  機能の ON/OFF と無関係である。

**元に戻すと。** 「どれか成功」に戻すと、上の表のとおり死活による切替が、経路が半分
壊れている状況で働かなくなる。「到達できないなら1回目で分かる」ので早期終了は不要だと
外す案も出うるが、外すと最悪の周期が25秒になり、周期の最小値より長く tick ループが
止まる。

**実機での状態。** JVM のテストは、「どれか成功で到達可能」に戻す・早期終了を外す・
予算の比較を変える・予算を外す、の各変異で落ちることを確認してある（実装時の記録）。
**実機では、この改訂後の死活による切替を一度も走らせていない**（`docs/MANUAL-TEST.md`
節 10 の N-8、節 11 の項目16）。「死活による切替は独立で正常に動く」という以前の確認は、
**この変更より前のビルド**についてのものである。

**場所。** `Ports.kt` の `runTimedCycle`（周期の進め方。既定実装と `TcpHealthProbe` の
両方が使う）、`TcpHealthProbe.probeTimed`、`FailoverService` の `PROBE_ATTEMPTS` と
`runGuardedProbe` の `apply`（`dispatch(ProbeResult(outcome.reachable))`）。
試験は `RunTimedCycleTest` / `HealthProbeTimedTest`。

## 19. 「測れないなら窓を捨てる」は、窓ごとに判断する（**効く場面は狭い。2026-10-09**）

**決めたこと。** `/proc/net/dev` が読めない・インターフェース名が引けない tick では、
**受信の窓だけ**を捨て（`PathQualityDetector.resetThroughput`）、**応答時間の窓は残す。**
トンネルの張り替えと、測る候補の入れ替わりでは、両方を捨てる（`reset`）。

**何が信じられていたか。** 裁定R20 は「測れないものは窓ごと捨てる」であり、
`FailoverService.sampleThroughput` には、測れなかったときの `reset()` が3か所あった。
判定器を `PathQualityDetector` に差し替えるとき、3か所を機械的に `reset()` に置き換える
のが素直に見える。

**実際はどうだったか。** 裁定R20 は**バイト計数器**についての裁定である。計数器が1 tick
読めなかったとき、応答時間（プローブ）はその tick にも測れていた。捨てる理由が無い。
`PathQualityDetector.reset()` は応答時間の窓も消すので、機械的に置き換えると、
計数器の読み取り失敗1回で最大60秒ぶんの応答時間の証拠が消える。

**判定を緩めない理由。** `isDegraded()` は先頭で `rx.windowAverage() ?: return false` を
返す。受信の帯は応答時間とは独立の連言なので、受信が測れないあいだは応答時間が何で
あっても判定は偽である。応答時間を残しても、「遅い」と**誤って言う**方向には何も働か
ない。影響するのは、受信の窓が埋まり直したあとに「遅くない」と**誤って言う**方向
——つまり取りこぼしの方向——だけである。

**⚠ これは既定の設定では、ほぼ何も変えない。** 緊急の修正ではなかった。

`SlowLinkDetector.windowAverage()` は、窓の最古と最新の差が60秒に満たないあいだは平均を
返さない。したがって読み取りの失敗のあと判定が真に戻るには、どのみち**60秒ぶんの
受信の再計測**が要る。既定のプローブ間隔30秒なら、その60秒のあいだに応答時間は
10サンプル貯まり直している。判定が真になる時点も、一周の記録が応答時間を読む時点も
（どちらも判定が真だった直後）、受信の窓が埋まっていることを含意するので、
応答時間の窓はすでに再び満ちている。

**効いてくるのは、`probeIntervalSec` が60秒に近づく・超える設定のときだけ**である
（設定できる範囲は10〜120秒）。間隔60秒では60秒の窓に最悪5サンプル（一周の記録の
最小サンプル数ちょうど。刈りは「窓より厳密に古い」ものだけなので周期が2つ入ることがあり、
最大10）、間隔120秒では0〜5サンプルで、応答時間のほうが律速になる。

**この項目の要点は「区別」であって「影響」ではない。** 初稿の理由書きは「一時的な読み取り
失敗のあと1〜2分は判定が偽になる」と書いていたが、**既定では起きない**と実装者が
指摘し、検算して訂正した（`PathQualityDetector.resetThroughput` の KDoc が条件つきの
正確な記述になっている）。**「正しくした」と「既定で効く」を混同しないこと。**
将来この項目を読んだ人が「既定でも重大な欠陥の修正だった」と受け取ると、無作用な
配置のために設計を曲げかねない。

**元に戻すと（`resetThroughput` を `reset` に統合すると）。** 既定では何も壊れたように
見えない。間隔を長くした利用者でだけ、読み取りの失敗のあとの応答時間の証拠が静かに
消え、**その候補が「最良へ戻す」の選定（サンプル数の門）から外れる**。気づく手段が
無い。逆に `resetThroughput` を「呼ばれていない」と思って消す人も出うる——呼んでいる
のは `sampleThroughput` の2か所（名前が引けない・読めない）で、**張り替え
（`iface != lastVpnIface`）は `reset()` のまま**である。この区別は
`FailoverServiceWiringTest` が原典のテキストで固定している。

**場所。** `PathQualityDetector.resetThroughput` / `reset`、
`FailoverService.sampleThroughput`。振る舞いの試験は `FailoverControllerLapRttWiringTest`
と `PathQualityDetectorTest`。

## 20. 速いと思って書かれた呼び出し側は、遅くした時点で全部見直す（**2026-10-09、実装の審査で発見。実機では未確認**）

**事実。** プローブ1周期の結果は、`runGuardedProbe` を通して適用する。**測っている
あいだに候補が入れ替わっていたら、結果を捨てる。** 門の鍵は `probeGuardKey` で、
`Verifying` の鍵だけが接続完了時刻（`connectedAtMs`）を含む。測り直しの鍵
（`slowLinkCandidateKey`）とは**別の関数**である。

**何が信じられていたか。** 改訂前、プローブ1周期は到達できればミリ秒で返った。呼び出し側
——結果を状態機械へ流す箇所——は、**測っているあいだに状態は動かない**と暗黙に
仮定して書かれていた。仮定は明示されておらず、コメントにも無かった。

**実際はどうだったか。** 複数回化で、1回目が成功した周期は最大 `probeTimeoutMs` × 2
（既定10秒）かかるようになった。`FailoverService` の scope は
`Dispatchers.Main.immediate` で、プローブは `Dispatchers.IO` へ suspend するので、
**周期の最中に外部イベント（コアの切断通知など）が状態遷移を進める。** 例:

1. `Healthy(A)` で周期が始まる
2. 1回目が成功したあと、コアが A の切断を報告し、`Connecting(B)` → `Verifying(B)` まで進む
3. 2回目以降が A の経路で詰まり、周期が10秒後に返る
4. 結果（到達可能）が **B に適用される**

害は3つ。

- **(a) B を一度も疎通確認せずに `Verifying` から `Healthy` へ昇格する。** しかも
  `Verifying` の門（`graceAfterConnectSec`、既定15秒）を丸ごと飛ばす。出荷済みの保証の
  違反である。
- **(b) A で測った応答時間が B の窓に入る。** `slowLinkCandidateKey` は `Verifying` と
  `Healthy` で同じ鍵を返すので、昇格では測り直しが走らない。5000 ms のサンプル1個で
  `spread > degradedJitterMs` を満たすため、B が健全でも切り替わりうる。
- **(c) 一周の記録に A のサンプルが B のものとして載り**、「最良」の選定が歪む。

**この窓は新しくない。** 失敗する周期は改訂前から約5秒かかっていたので、
`reachable = false` が違う候補へ当たる余地はあった。複数回化が、成功する周期にまで
窓を広げ、応答時間の混入という新しい経路を足した。**窓が広がって初めて害が出る形になった。**

**どう見つかったか。** 審査（実装を読む別の目）が見つけた。型はこれを教えない
（結果の型は何も変わっていない）。テストも教えない——プローブの所要時間のあいだに
状態が動く場面を作る試験が、それまで無かった。

**2段階で閉じた。** 最初の門は `groupId#candidateIndex` を比べた。実装者が自分から
開示した穴が残っていた——**同じ添字へ張り直した場合**（`Healthy(g,i)` → 切断 →
`Connecting(g,i)` → `Verifying(g,i,T)`。利用者の切断・自動接続・全滅後の再試行が先頭へ
戻る経路で、先頭が現候補と同じなら起きる）は鍵が変わらず、(a) が起きる。そこで
`Verifying` の鍵だけに `connectedAtMs` を足した。世代カウンタは要らない（状態が既に
持っている値で足りる）。

**一般化（この項目が残る理由）。** **ある操作の所要時間を変えたら、その操作の速さを暗黙の
前提にしている呼び出し側を数え上げる。** 型もテストも、この種の前提は教えてくれない
——前提は書かれていないので、壊れても何も落ちない。複数回化の検討で、数え上げて
見つかったのは次の2つだった: (1) tick ループが止まる時間（予算で解決。項目18）、
(2) 結果の適用先（この項目）。**他に「プローブは速い」を前提にしている箇所が無いかを
網羅的に調べた記録は無い。** 次に誰かがプローブや周期の長さを変えるときは、この2つを
手本に、同じ列挙をやり直すこと。

**捨てる方向が安全な理由。** 候補Aで測った結果は候補Bについて何も言わない。止まるものは
無い——`Verifying` は猶予が明ければ自分でもう一度プローブする（本来そうあるべき姿）。

**元に戻すと／統合すると。** 門を外すと上の3つの害が戻る。**`probeGuardKey` と
`slowLinkCandidateKey` を統合しないこと**——前者は `Verifying` で接続完了時刻を含めねば
(a) が閉じず、後者は含めると `Verifying` → `Healthy` の昇格で判定器が空になり、
`Verifying` のあいだに集めた証拠を捨てる。違う答えを要るから別の関数である。
`slowLinkCandidateKey` の本体に `connectedAtMs` が現れないことを、`FailoverServiceWiringTest`
が原典のテキストで表明している。

**実機での状態。** 候補の入れ替わりと周期の競合は、JVM の試験が決め打ちの列で再現して
いる。**実機で観測したことは無い**（再現には、プローブが走っている最中に接続先を
切らせる必要がある）。

**場所。** `ProbeCycleGuard.kt`（`runGuardedProbe` / `probeGuardKey`。KDoc に組み合わせの
表がある）、`FailoverService` のプローブ周期。試験は `FailoverControllerLapRttWiringTest` と `FailoverServiceWiringTest`。

## 21. 判定の窓（60秒）を設定項目にしない

**決めたこと。** 判定の窓の長さは `PathQualityDetector.WINDOW_SEC = 60` の定数で、
`SlowLinkSettings` に項目を置かない。画面は**読む**が、利用者は**変えられない**。
改訂版仕様の設定項目（§4-A）が4つ増えたとき、窓の長さは入らなかった。

**なぜ。** 可変にする案を外した。理由は3つ。

- **二重管理になる。** 設定画面の導出文は「…状態が 60 秒続いたときに切り替えます」と
  言う。この数字は `SettingsText.pathQualitySummary` が `WINDOW_SEC` から導く（文面に
  `60` を直書きしない）。窓を可変にすると、導出文は設定値に追従せねばならなくなり、
  直書きに戻ると窓を変えたとき画面だけが古い値を言い続ける。`SettingsTextTest` が、
  既定の引数が `PathQualityDetector.WINDOW_SEC` そのものであることを原典のテキストで
  固定している（`const val` は試験から書き換えられないので、振る舞いでは `= 60` と
  区別できないため）。
- **窓を長くしても、比較の記録を得る手段にはならない。** 候補を比べる記録（一周の
  あいだの候補ごとの応答時間）が欲しいのは、候補あたりのサンプル数である。それは
  **採取の回数を増やす**（1周期の接続を3回から5回へ）ことで得た。仕様書 §2-A は、
  窓を延ばして一周を15分にする案より、TCP 接続が30秒あたり5本に増えるほうが「桁違いに
  安い」としている。**検知の窓と、比較の記録は別物である。**
- **利用者が調整して意味のある値ではない。** 旧仕様 §5 の判断（窓の長さと送信側の閾値は
  定数にする。設定画面に項目を増やすと操作しづらい）を引き継いだ。

**気づきにくい帰結。** 窓が60秒なので、判定が成立するまでひとつの候補に**おおよそ60秒
以上**いる。旧判定の実測では、切替の間隔は約60〜65秒だった（10-3-2。**旧判定**の
値で、新しい判定の間隔はまだ測っていない）。利用者が「もっと早く切り替えたい」と窓を
短くしたくなる場面はありうるが、それは仕様の変更であって、設定を足せば済む話ではない。

**元に戻すと（＝設定項目にすると）。** 導出文の二重管理が最初に壊れる。加えて、4項目の
既定値の根拠（旧仕様 §2-2 の実測）は、窓が60秒であることを前提にした1台の端末・
1つの宛先・1つの時間帯の値であり（仕様書 §4-A）、窓を動かせるようにすると、その
前提が利用者の設定によって黙って変わる。

**場所。** `PathQualityDetector.WINDOW_SEC`、`SettingsText.pathQualitySummary` の
`windowSec` 引数。

## 22. 一周の終わりに最良へ戻す切替は、予算に数えず、判定が成立しているときだけ行う

**決めたこと。** 一周の終わり（前へ進む道が尽きたとき）に、判定が真なら、応答時間が最良
だった候補へ戻す（`returnToBest`）。この切替は**一周の予算（メンバー数 - 1。項目6）に
数えない**（`recordSlowLinkSwitch` を呼ばない）。次の条件がすべて揃ったときだけ動く。

- **判定が成立している**（`slowLinkProvider()` が真）。
- 前方に起動できる候補が無い、または予算を使い切った。
- **この一周で前へ進む切替を1回以上している。**
- 戻り先が現候補と**違う**。同じなら切り替えない。
- 戻り先は**無人で起動してよい候補**に限る（安全策 S1 の除外集合と、初回ログイン未了の
  候補は、記録上は最良でも選ばない）。

戻る切替は**一周に一度だけ**で、行った時点（または戻り先が現候補で行わないと決めた時点）
で一周が「止まった」と刻まれる。

**なぜ。** 次を外した。

- **予算に数える案。** 予算は「前へ進む切替」の数で、判定の誤りが候補の間を延々と
  往復するのを止める上限である（項目6）。戻る切替は上限に達した**あと**の、一周に一度
  だけの終端の動きなので、数えると予算の意味が「前進の回数」でなくなる。戻る切替は
  別の上限（一周に1回、前進のあとだけ）で縛る。不変条件テスト I5 は、前進を
  メンバー数 - 1 まで、戻りを一周1回までと、**別々に**数える。
- **判定が偽でも、予算が尽きたら戻す案。** 実装者が、計画の字義どおりだと**健全な最後の
  候補を「予算が尽きたから」だけで捨てる**ことを発見した。切り替える理由が無いのに
  切断を作るのは、この機能の目的に反する。**戻すのは「遅い」と判定されているときだけ。**
- **切替が1回も無かった一周でも戻す案。** 比べる相手が無い。実装者が、計画の規則では
  既存の試験2件が落ちることを見つけ、試験を曲げずに規則を直した。
- **戻り先を「グループの先頭」にする案（サンプルが不足するとき）。** 先頭が除外されて
  いたり初回ログイン待ちだったりすると、そこへ戻すのは裁定93/94 と不変条件 I1 が禁じる
  「人が居なければ成功しえない候補を機械が起動する」ことになる。戻り先は「**無人で
  起動してよい最初のメンバー**」である。

**⚠ 守っているのは何か。** 「戻る切替は予算に数えない」は、**コントローラの観測できる
挙動には現れない**（戻る時点で一周は既に止まっているので、数えても数えなくても挙動が
同じである）。この決定を守っているのは、I5 の分類（着地した場所が前方なら計数、後方または
同値なら戻り）と KDoc だけである。実装者が正直に報告した盲点で、受け入れてある。

**元に戻すと。** 「予算が尽きたら無条件で戻す」にすると、健全な候補を捨てる。
「予算に数える」にしても現状の挙動は変わらないが、予算の意味が前進の回数でなくなる。

**画面の見え方。** 戻る切替も、画面に「直前の切替: 経路品質で切替」と出る（項目11 の
追記）。前へ進んだ切替と見分けがつかない。接続先の名前の変化で読むこと。

**実機での状態。** 戻る切替は実機で**一度も観測していない**（`docs/MANUAL-TEST.md` 節 10 の
N-4）。戻り先の選択（応答時間の順位付け）は、候補ごとの測定時刻がずれる限界を持つ
（仕様書 §2-A「残る限界」）。

**場所。** `FailoverController.returnToBest` / `onSlowLinkSwitch`、`LapRecord.bestUuid`
（順位付けは推移的な2段の規則。1対1の比較に戻さないこと——仕様書 §2-A に循環の反例）。
機械生成側は `FailoverControllerInvariantTest` の I5。

## 23. 一周のあとの再開の時計は、裁定78 / 項目3 の禁止に当たらない

**決めたこと。** 設定項目 `rearmAfterLapMin`（0〜240分、刻み15。**既定は 0＝再開しない**）が
あり、一周が止まってから設定した分が経つと、そのグループの一周の記録を**消す**
（`maybeRearmLap`）。**消すだけで切り替えない**——切替には判定の3条件が別途要る。

**これは旧仕様 §4-5 の「時間による自動解除は設けない」を覆している。** 旧仕様は
`FailoverController` の KDoc と実装計画にも同じ趣旨を書いていた（旧仕様と計画には覆した旨
の注記を足した。`FailoverController` の KDoc は改訂済み）。理由は「遅いという判定は
誤りうるので、誤判定のまま時間で再武装すると候補の間を延々と行き来し続ける」で
あった。覆した根拠は2つ（仕様書 §2-B）: (1) 判定の根拠が変わり「誤りうる」という前提が
弱まった（消えてはいない）。(2) 再開は「切り替える」ことではなく、**資格を戻すだけ**
なので、状況が改善していれば何も起きない。劣化が続いているときだけ、利用者が決めた
間隔ごとに一周ぶんの切断が起きる。

**なぜ項目3 に当たらないか。** 項目3 は「**人が居るか**」「**その指示がまだ生きているか**」
の答えを時計から取ることを禁じる。**この時計はそのどちらでもない。** 自動動作の冷却
期間であり、`connectTimeoutSec` や `graceAfterConnectSec` と同じ種類の、正当な
**期限**である（項目3 の「誤読しないこと」が、時計による締切は存在すると書いている）。
人が居るかどうかには触れず、認証ダイアログの前で何かを切ることもない。

**⚠ 将来これを見た人が、項目3 違反として消さないこと。** 項目3 の趣旨が「時計で人の
在席を判定した」過去の誤りの再発防止である以上、この時計を同じ型の誤りと読むのは自然
だが、**禁じられた用途と違う**。逆に「既定の間隔を短くして常に再開する」のも誤り
——既定は 0（再開しない）で、現在の挙動を変えず、望む人だけが有効にする。

**既存の解除経路は据え置く。** 利用者の明示的な接続、グループ構成の変更、本機能の設定の
変更（`rearmAfterLapMin` 自身の変更を含む）。**設定を変えると記録が消える**ので、
再開の確認をするときは設定を先に済ませてから一周を走らせること（`docs/MANUAL-TEST.md`
N-5）。

**場所。** `FailoverController.maybeRearmLap`（KDoc に項目3 との関係がある）、
`SlowLinkSettings.rearmAfterLapMin`、`SettingsStepper.stepRearmAfterLapMin`。
再開は**実機で一度も観測していない。**

## 24. VPN のインターフェースが2本見えると、経路品質の判定は黙って無効になる（**既知の限界。2026-10-09、枝全体の最終レビューで発見**）

**何が起きるか。** `selectVpnInterfaceName`（`VpnInterfaceName.kt`）は、
`TRANSPORT_VPN` のネットワークから得られる名前が**2つ以上に分かれていたら
null を返す**。これは意図した設計である——どちらを測ればよいか分からないので
「測れない」と答える。`null` を「遅い」と解釈しないのが項目15 以来の原則である。

問題は、その状態が**続いた**ときである。`sampleThroughput` は毎 tick で null の
分岐に入り、受信の窓は埋まらず、`PathQualityDetector.isDegraded()` は
最初の行（`rx.windowAverage() ?: return false`）で常に偽を返す。
つまり**機能は恒久的に発火しない。画面は「ON」と出たままで、何の表示も無い。**
設定画面の導出文は、評価されることのない閾値を説明し続ける。

**死活判定による切替は影響を受けない。** あちらはインターフェース名を読まない
（プローブはトンネル越しの TCP 接続だけを見る）。したがってアプリは
**完全に健全に見える。**

**なぜ直さないか（2026-10-09 の判断）。**

1. **Android は同時に1本の VPN しか許さない**ので、2本が**恒久的に**見える配置は
   実機で起きにくい。
2. **一過性の曖昧さ**（トンネルを張り替える最中に古いネットワークが残る）は
   項目19 の修正で無害になった。名前が引けない tick では受信の窓だけを捨て、
   **応答時間の窓は残る**ので、曖昧さが解けた直後から判定を続けられる。
   枝の最後にこの欠陥（`reset()` が先に走って応答時間まで消えていた）を直してある。
3. 残るのは「2本の VPN が本当に同時に動いている利用者」だけであり、
   そのために**枝の最後に新しい画面表示を足す代償の方が大きい**と判断した。

**間違っていた場合の代償。** その配置の利用者には、設定を ON にしても
何も起きない。**既定は OFF なので、何もしていない利用者には影響しない。**
死活による切替は従来どおり働く。

**直すなら。** 「いま測れていません」を利用者の見える場所
（前景通知の文、またはホームの行）に出すこと。**黙って無効なのと、
静かに条件を満たしていないのとを、利用者が区別できるようにするのが要点**である。
閾値をいじらせるのではなく、測定が成立していないことを言う。

**場所。** `VpnInterfaceName.selectVpnInterfaceName`（`distinct().singleOrNull()`）、
`ConnectivityVpnInterfaceName`、`FailoverService.sampleThroughput`。
**実機では未確認**（2本の VPN を同時に動かす確認は行っていない）。

## 25. 接続直後のバーストが最初の窓に入る——猶予が窓より短い（**2026-10-10 に実機で露呈。未解決**）

**何が起きたか。** 2026-10-10 の N-1（待機中に切り替わらない）が**不合格**になった。
機能 ON・**設定は既定値**・観測側の通信なし・32分の待機で、
**経路品質起因の切替が1回起きた**（`docs/MANUAL-TEST.md` 節10 の N-1 2回目の記録）。

約90区間のうち**受信が下限（50 kbps）を超えた区間は1つだけ**で、それは
**トンネルが上がった直後の23秒間（約504 KB、175.4 kbps）**だった。
接続確立に伴う端末自身の通信（接続性の検証・名前解決・VPN 復帰で再開した同期など）で、
**利用者は何もしていない。** バーストが窓から抜けたあとは 0.1〜0.3 kbps で、
30分間何も起きていない。

**原因。猶予と窓の長さが噛み合っていない。**

- 接続直後の猶予は **15秒**（`FailoverConfig.graceAfterConnectSec`）。
  判定を**15秒だけ**遅らせる。
- 判定の窓は **60秒**（`PathQualityDetector.WINDOW_SEC`。項目21 のとおり設定項目にしない）。
- 判定器は候補が変わると窓を空にする（`syncSlowLinkCandidate`）。
  **つまり窓は接続の瞬間から埋まり始める。**

したがって **接続から60秒後に下される最初の判定は、その大半が接続確立のバーストで
構成されうる。** 高遅延の経路では、**接続するたびに1回、待機中の切替が起こりうる。**

**改訂は重さを下げたが、無くしていない。** 旧判定（項目17）は待機中に
**6候補を歩き切った**。改訂後は**1回で止まった**——応答時間の条件が候補ごとに違うからである。
ただし止まったのは次の候補のばらつきが閾値未満だったからで、**設計上の保証ではない。**
ばらつきの高い候補が複数並ぶグループで連鎖しないことは**確認できていない。**

**考えられる方向（どれも未検討。再開するときの入口）。**

1. **猶予を窓以上にする**（15秒 → 60秒以上）。最も素直だが、
   **検知までの時間が延びる**（画面の文面と仕様書 §2 の「60秒続いたとき」に影響する）。
2. **接続直後の一定時間を窓から除く**（例: 最初の30秒の採取を窓に入れない）。
   猶予は変えずに済むが、**判定器に「接続からの経過」という新しい入力が増える**。
   いまの判定器は時刻を引数で受け取るだけで接続を知らない（その作法を崩す）。
3. **帯の内側の窓が1つでは発火させない**（連続2窓を要求する）。
   バーストは1窓にしか入らないので効く。代償は**検知が倍遅くなる**こと。
4. **接続直後のバースト自体を減らす。** これはアプリの外（Android の接続性検証や
   他アプリの同期）なので、こちらから制御できない。

**どれを採るかは、検知の速さと待機中の静けさのどちらを取るかの判断である。**
本仕様は「待機中に切り替わらない」を**改訂の目的そのもの**として掲げた（仕様書 §1）。
その目的が実機で達成できていないので、**次に手を入れるならここが入口である。**

**場所。** `FailoverConfig.graceAfterConnectSec`（15秒）、
`PathQualityDetector.WINDOW_SEC`（60秒）、`FailoverService.syncSlowLinkCandidate`（候補が変わると窓を空にする）、
`FailoverController.onSlowLinkSwitch`（猶予の門）。

**既定は OFF のまま。** この項目が解決するまで、既定を変えてはならない。
