# 手動テスト手順と実機での観測結果（Fire TV）

このドキュメントは、TV UI（リモコンだけで完結する D-pad 操作）と接続の通し確認について、
**実機で実際に行った手順と、そのとき観測した値**を、利用者が再現できる形に書き起こしたものである。

> **接続先の名前について。** この文書に出てくる接続先の表示名は
> **`候補A`〜`候補I` の仮名に置き換えてある**（実機で使った名前は、事業者名や
> 拠点が分かるため公開リポジトリには残さない）。置き換えは**一貫している**ので、
> 同じ仮名は常に同じ接続先を指し、**記録の構造——どの候補からどの候補へ
> 切り替わったか——はそのまま読める**。`unreachable` のように
> この確認のために作った名前はそのまま残してある。
> 宛先の例に使う IP は RFC 5737 の `192.0.2.1` など、ドメインは `.invalid` である。
>
> **この対応は「この文書の記録の中で」一貫している。** 仕様書や設計の文書に出てくる
> `候補A` `候補B` などは、**説明のための一般名**（「速かった候補」「遅かった候補」）であり、
> この文書の `候補A`〜`候補I` と同じ接続先を指すとは限らない。混同しないこと。

- 実機: **Fire TV Stick 4K（API 25 / 1920x1080）**、リモコンのみで操作
- 対象ビルド: 各節に記載。最終確認は **`ef87ee2`**（節 2-1 / 3-2 / 3-4）
- ここに「✅ 確認済み」と書いてあるものは**すべて実機で観測した結果**である。
  観測していない項目は「未確認の項目」（節 11）にまとめてあり、そこに挙がっているものは
  **確認していない**。
  初回ログインの門番は節 9、経路品質の低下による切替（旧称: 速度低下による切替）は節 10 に別立てである。
  **節 9 は節 9-3 の5項目のうち3つが確認済み**（2026-10-07。結果は節 9-3-1〜9-3-3）で、
  残りは**実在するサーバとパスワード入力が必要なため未実施**。
  **節 10 は2部に分かれる。** 後半は**古い判定（受信速度と送信速度）**を実機で走らせた記録
  （切替が動いた・待機中に誤判定した、など。2026-10-08〜09）。前半は**2026-10-09 に
  根拠を変えた新しい判定（応答時間とそのばらつき）**の確認手順 N-1〜N-8 で、
  **新しい判定については、実機で何も確認していない（全項目が未実施）。**
  古い判定の ✅ を、新しい判定の確認として読まないこと。

座標（`[左,上][右,下]`）は `uiautomator dump` で読み取ったフォーカス矩形で、1920x1080 での値である。
利用者が手順を再現するときに座標は不要で、フォーカスがどこに乗るかの根拠として残してある。

## 0. 前提

1. `docs/BUILD.md` の手順で `app-debug.apk` をビルドし、端末にインストールする。
2. ホーム画面（アプリ一覧）から本アプリを起動する。
3. **端末の言語は `en-US` にしておく。** `ja-JP` では端末側の IME が
   `libWnnWrapper.AMAZON.so` を読めず `UnsatisfiedLinkError` で落ちることを観測した
   （端末側の欠落であり、本アプリの問題ではない）。`en-US` ではこのクラッシュは起きず、
   ASCII が変換されずそのまま入る。
4. **ソフトキーボードが出ないときは、まず端末を再起動する。** IME ウィンドウが
   `Surface: shown=false` のまま居座って BACK を食い続ける状態を観測しており、
   再起動で復旧した（節 1 の脚注参照）。

## 1. 接続先の追加（文字入力とソフトキーボード） ✅ 確認済み

**手順**（リモコンのみ。ビルド `5f5cfdc` 以降で確認）

1. ホーム画面で `＋ 接続先を追加` にフォーカスを合わせ、決定。
2. 初期フォーカスは `サーバ URL（例: vpn.example.com）` の**行**に乗る
   （テキスト欄そのものではない）。ここで決定を押す。
3. ソフトキーボードが出る。`test.example.com` を入力する。
4. **BACK を1回** → キーボードが閉じる。
5. **BACK をもう1回** → 編集モードが終わり、行にフォーカスが戻る。**入力値は保持される。**
6. DOWN → `表示名（任意）` の行。
7. DOWN → `保存`。決定。
8. 一覧に `test.example.com` が現れる。

**観測結果**

- 手順3 でキーボードが出ていることの判定は、画面を見るか、
  `dumpsys window` の `InputMethod` ウィンドウの `mViewVisibility=0x0(VISIBLE)` と
  `mHasSurface=true` で行う。**`screencap` は IME レイヤを含まないので判定に使えない。**
- BACK が2回必要なのは正しい（1回目は IME が消費して閉じる、2回目が編集モード終了）。
- 保存後のプロファイルに `batch_mode=empty_only` と `server_address=test.example.com` が
  書かれていることを、`profile-<uuid>.xml` を読んで確認した。この値が無いと再接続ごとに
  認証ダイアログが出て自動フェイルオーバーが止まる（仕様書 9.2）。
- **表示名を空のまま保存すると、表示名はサーバ URL から導出した既定名になる**
  （`test.example.com` → `Example`）。

> 脚注（キーボードが出ない場合）: 本アプリ側の必要条件は「明示的な表示要求」で、
> `showSoftInput(editText, 0)` を使っている（暗黙要求 `SHOW_IMPLICIT` では
> Fire TV のフルスクリーン IME が要求を拒否することを実機で確定させた）。
> それでも出ない場合は端末側の IME が壊れている可能性があり、再起動の前後で
> `Surface: shown` が `false` → `true`、`mDrawState` が `READY_TO_SHOW` → `HAS_DRAWN`
> に変わることを観測している。

## 6. 接続の通し確認 ✅ 確認済み（`b60606e`）

**手順**

1. 接続先を3件追加する（この確認では `unreachable` / `候補H` / `候補I`）。
2. グループを1つ作り（この確認では `テスト群`）、候補を**優先順**に並べる:
   `unreachable` → `候補H` → `候補I`。`自動切替: ON`。
3. ホーム画面でそのグループの行に決定を押して接続する。
4. グループ行のバッジと、`tun0` の状態を時間を追って観測する。

**観測結果**

```
[15s] 接続中 (unreachable)        tun0: なし
[30s] 接続中 (unreachable)        tun0: なし
[45s] 疎通確認中 (候補H)       tun0: inet 10.10.10.38
[60s] 接続済み (候補H)         tun0: inet 10.10.10.38
...   [300s] まで安定
```

先頭候補（`unreachable`）では `tun0` が張られず、次候補（`候補H`）でトンネルが張られ、
`疎通確認中` → `接続済み` と進み、300秒まで安定していた。
**画面に出ている候補名とバッジが、実際の `tun0` の状態と一致している**ことをこの観測で確認した。

なお、接続状態の表示がホーム画面に追従すること自体は別の機会にも確認している
（`接続中 (unreachable)` → `接続済み (候補H)`）。Fire TV には通知シェードが無いため、
接続状態はこのグループ行の表示だけが手がかりになる。

## 7. 初回ログイン（認証ダイアログ）✅ 確認済み（`287d035`）

利用者の報告「接続先を削除して再登録したらパスワード設定画面が表示されない」から、
連鎖する4つの欠陥（裁定92〜95）が見つかった箇所である。**資格情報が保存されていない
接続先でしか再現しない**ので、確認には未ログインの接続先が要る。

### 7-1. 手順

1. 資格情報が未保存の接続先を、グループの候補に入れる
2. ホームでそのグループの行に**決定**（個別の接続先は単体では接続できない）
3. 証明書の警告が出たら、内容を確認して承認する
4. ユーザー名を入力して OK
5. パスワードを入力し、**「パスワードを保存」にチェックして** OK

### 7-2. 実機で観測した結果

| 見るところ | 結果 |
|---|---|
| 認証ダイアログが TV 画面に出る（裁定92） | 出る |
| ゆっくり入力しても打ち切られない（裁定93・94） | 打ち切られない |
| OK のあと、**別の接続先のログイン画面が出てこない**（裁定95） | 出てこない |
| 最後まで進む | `接続済み` に到達 |
| 残存ダイアログ | 0枚 |
| 資格情報・証明書の保存 | `FORMDATA-*` / `ACCEPTED-CERT-*` が書かれる |

> 手順4→5 のあいだで打ち切られないことが要点である。ユーザー名とパスワードは
> **別々のダイアログ**で、修正前は両方に答える時間が合計45秒しかなかった。

### 7-3. 修正前の症状（再現したときの見え方）

```
表示中           「（接続先A）login / Please enter your username.」
 ↓ キャンセル
下から出現       「（接続先B）login / Please enter your username.」
 ↓ キャンセル
本当の状態       「4 件の候補 · 自動切替 ON / 疎通確認中 （接続先C）」
同時に           tun0 は別候補で既に接続済み
```

見捨てた候補のダイアログが積まれ、1枚答えると次が現れるため「ループしている」
ように見えた。文面が `Login failed.` ではなく `Please enter your username.` で
あることが、拒否の再提示ではなく**別スレッドの新しい認証列**である手がかりになる。

## 8. 消灯と点灯の往復 ✅ 確認済み（`287d035`）

```
消灯前   接続済み           tun0 inet 10.0.0.222
消灯     5秒以内に tun0 消滅。30秒間そのまま（mWakefulness=Asleep）
点灯     6秒で tun0 復帰 → 疎通確認中 → 接続済み
         残存ダイアログ 0枚。保存済みなので再入力を求められない
```

裁定92 で `VPNConnector` による bind を足したあとも、**裁定44（消灯時は切断する）は
壊れていない**ことの確認である。bind は `stopService` を無効化しうるため、
ここと「TV 画面を前面にしたままの切断」は bind を変更したら必ず measure し直すこと。

## 9. 初回ログインが必要な接続先を自動切替が飛ばすこと △ **一部確認済み**

資格情報が保存されていない接続先を無人で起動しないようにした変更の確認である。
**節 9-1 と節 9-2 の項目は実機で観測していない。** 節 9-3（接続先の行からの
「初回ログイン」）は一部を 2026-10-07 に観測した（結果と限界は節 9-3-1）。
**それ以外を「動く」と判断してはならない。**

背景: 利用者が6件のグループに未ログインの接続先を追加したところ、ユーザー名の
あとにパスワード画面が出なかった。端末の統計ではその接続先だけが**8回試して8回とも
「取り消し」**で終わっており、最後の試行は VPN スレッド開始の**11.8秒後**に
`User canceled auth dialog` へ落ちていた。11.8秒は裁定30 の10秒
（`USER_PROMPT_WAIT_MS`）である。約2分間隔でグループを巡回して先頭へ戻るたびに、
その候補が無人扱いで起動され、裁定95 が入力中のダイアログを畳んでいた。

判定は「そのプロファイル自身の prefs に `FORMDATA-` で始まるキーが1つも無いか」で
行う。値は読まない。端末の9プロファイルでキーの**個数だけ**を数えたところ、症状の
出ている1件が **0個**、正常に使えている8件はいずれも **3個**で、判定基準は実機の
サンプル上で完全に分離していた（2026-09-28）。この数え上げは判定の裏取りであって、
以下の**動作の確認ではない**。

### 9-1. 手順（未実施）

前提: 資格情報が未保存の接続先を1件と、**すでにログイン済みの接続先を2件以上**
用意し、3件以上のグループにまとめて自動切替を ON にする。

1. **表示**: ホームの一覧で、未ログインの接続先の行に
   `初回ログインが必要 / 自動切替では選ばれません`
   と出ていること（**これで全文である。** 解き方は隣の `初回ログイン` のカードが
   示すので注記には書かない——注記が長いと本体カードが操作カードを押し出すため、
   `4cf517c` でこの長さに縮めた。`HomeRows.firstLoginNotice` が出す文言そのもので、
   `HomeRowsTest` が文言ごと固定している）。ログイン済みの行には出ていないこと。
2. **利用者の操作では飛ばさないこと**: その行の **→** で隣の `初回ログイン` に移り
   **決定**する（節9-3 の手順。グループの先頭へ動かす必要はもう無い）。確認で
   `接続する` を選ぶと、その接続先の認証ダイアログが出て、**10秒で消えないこと**
   （節7 と同じ手順でユーザー名 → パスワードを入力し、「パスワードを保存」に
   チェックして進む）。
3. **自動の巡回では飛ばすこと**: 手順2 を**行わずに**、未ログインのまま
   自動切替に巡回させる（ログイン済みの候補をわざと落として次へ進ませる、または
   消灯→点灯で `AutoConnectGroup` を起こす）。未ログインの接続先が
   **一度も起動されない**こと（`adb logcat` に `User canceled auth dialog` が
   出ないこと、候補名にその接続先が出ないこと）。
4. **初回ログイン後は巡回に戻ること**: 手順2 を終えて `FORMDATA-*` が
   書かれたあと、**アプリを再起動せずに**ホームの行から注記が消え、手順3 と同じ操作で
   その接続先が通常の候補として起動されること。注記が消える契機は接続の節目
   （`Connecting` → `Verifying` → `Healthy`）であり、疎通確認そのものでは
   引き直さない（`HomeRows.firstLoginRecheckKey`）。

### 9-2. 全員が未ログインの場合（未実施）

グループの全メンバーが未ログインの状態で無人の開始（消灯→点灯）を起こすと、
起動できる候補が無いので既存の枯渇（`Exhausted`）に入る。**新しい経路は作って
いない。** ホームのバッジは `再試行待ち` になり、再試行の間隔は 30秒 → 1分 →
2分 …… と倍々に伸びて10分で打ち止めになる（`Backoff`）。接続試行はゼロのまま
なので認証ダイアログは1枚も出ない。ここから回復するには**利用者がホームで
そのグループに接続する**（その経路では飛ばさないため）。
この挙動は JVM のユニットテストでのみ確認しており、**実機では未確認である。**

### 9-3. 接続先の行からの「初回ログイン」 △ **一部確認済み（2026-10-07）**

未ログインの接続先がグループの2番目以降にあると到達する手段が無かった
（有人の接続は必ず先頭メンバーから始まり、接続先を単体で繋ぐ操作が無かった）。
その穴を埋めるために足した操作の確認である。

**5項目のうち、項目1・項目5・項目3 の前半を 2026-10-07 に実機で観測した**
（結果は節 9-3-1 / 9-3-2 / 9-3-3）。**項目2 と項目4 は未実施**で、どちらも
実在するサーバとパスワード入力を要する。項目3 の後半（認証ダイアログを開いたまま
連打する確認）は、**書かれたままでは実行できないことが分かった**（節 9-3-2）。

観測していない部分について確認できているのは JVM のユニットテスト（開始位置を
指定した有人接続・範囲外の扱い・文言・複数グループの選び方・印の2段の進み方・
押した時点での拒否）とビルドだけである。

前提: 未ログインの接続先を**グループの2番目以降**に置き、同じグループに
ログイン済みの接続先を1件以上入れておく（自動切替は ON のままでよい）。
**手順2・3 は「VPN に接続している状態から」必ず1回行うこと。** 印の生死は
切断状態から実行した場合と接続状態から実行した場合で通る経路が違い
（接続状態からは Ruling 25 の2段階切替が1枚挟まる）、切断状態でしか試さないと
二度押しの確認が偶然通ってしまう。

1. **操作が出ること（✅ 確認済み。カードの位置は節 9-3-1、D-pad は節 9-3-3）**:
   ホームの一覧で未ログインの接続先の行に注記
   `初回ログインが必要 / 自動切替では選ばれません`
   （節9-1 の手順1 と同じ全文）が出ており、その行で **→** を押すと隣の
   `初回ログイン` / `決定で接続` のカードにフォーカスが移ること。**→ と決定だけで
   到達できること**（長押しは使わない。長押しは従来どおり削除の確認が出る）。
   `←` で本体のカードに戻れること。他の行では **↓** で次の行へ移れること
   （行内に2枚並べたことで上下移動が壊れていないこと）。
2. **確認と認証画面（未実施）**: `初回ログイン` で**決定**すると確認が1枚出て、
   `「<接続先名>」で初回ログインしますか？` に続けて
   `いまの VPN 接続を切り、グループ「<グループ名>」経由で繋ぎ直します。認証画面が出たら入力してください。`
   と書かれていること（初期フォーカスは `キャンセル` 側。**「キャンセル」と
   「接続する」の両方が画面内に見えていること**——本文が長いとボタン行が
   下にはみ出す）。`接続する` を選ぶと
   **いまの接続が切れてその接続先が起動し**、認証ダイアログが出ること。
   `キャンセル` または BACK では何も起こらず、フォーカスが元の行へ戻ること。
   接続中に実行した場合は、切断の完了を待ってから**その接続先**が起動すること
   （先頭のメンバーではないこと）。
3. **二度押しができないこと（前半は確認済み——節 9-3-2。ここが一番重要。必ず
   接続済みの状態から）**:
   `接続する` を選んだ**直後**に、その行から `初回ログイン` のカードが消えて
   `初回ログイン中 / 認証画面で入力してください（押し直し不要）`
   に変わっていること。**接続済みの状態から実行した場合は、切断 →
   切断確認 → ダイヤル → 認証画面までに数秒〜数十秒かかる。そのあいだ一度も
   カードが戻らないこと**（戻るなら二度押しの窓が残っている。ホームのバッジが
   `接続中` になる前の段階を含めて見ること）。**認証ダイアログを開いたまま**
   その行へ戻って何度 →・決定を押しても、ダイアログが消えないこと（消えるなら
   窓が残っている。それは節9 の症状——入力中にパスワード画面が消える——の
   再現である）。
   認証をキャンセルするか接続が失敗したあとは `初回ログイン` のカードが**戻って
   くること**（＝再試行できること）。ただし**キャンセルした瞬間ではない**:
   その候補の試行が打ち切られて次の状態（`FailingOver` など）へ進んでから戻るので、
   数十秒かかることがある。接続先やグループの編集画面へ入って戻ると、この
   「初回ログイン中」は消えて操作が戻る（画面側だけの印なので意図どおり）。
   **押した時点でメンバーが外れていた場合**（別の画面や旧 UI でそのグループから
   外したあと、ホームの行から実行した場合）は、「初回ログイン中」にならず
   `「<接続先名>」はグループ「<グループ名>」から外れています。一覧を読み直します。`
   が画面上部に出て、行が最新の状態に更新されること。
4. **ログイン後に表示と操作が消えること（未実施）**: ユーザー名とパスワードを
   入力して（「パスワードを保存」にチェック）接続できたあと、**アプリを再起動せずに**
   その行から注記と `初回ログイン` のカードが消え、以後は自動切替の巡回で
   通常の候補として起動されること（節9-1 の手順3・4 と同じ確認）。
5. **グループに属さない接続先には何も出ないこと（✅ 確認済み 2026-10-07）**:
   どのグループにも入れていない未ログインの接続先の行には、注記も
   `初回ログイン` のカードも出ないこと（自動切替の対象ではないので
   飛ばされることもない）。
   **観測:** 未ログインの接続先をグループから外すと、行の表示は
   接続先名・サーバ URL・`長押しで削除` の3行だけになり、
   **他の行とまったく同じ形になった**（注記もカードも画面上に存在しない）。
   逆向きも確認した——接続先を作っただけでは注記は出ず、**グループに追加した
   時点で出る。** この順序を知らないと「表示されない不具合」と読み違える。

複数のグループに属している接続先では、**グループ一覧の順で最初のグループ**の名前が
確認の文面に出る（そのグループを経由して繋ぎ直す）。これも未実施である。

#### 9-3-1. 実機で観測した結果（2026-10-07、`74bb018` のビルド）

端末に入っている APK がこの機能を含むビルドと同一であることを md5 で照合した上で
行った。**値（認証情報）は一切読んでいない。** 判定の入力は `FORMDATA-` で始まる
**キーの個数だけ**を数えて確認した。

準備として、**実在しないサーバ URL（`test.invalid`）の接続先**を1件作り、
7件のグループの**7番目**（最後）に置いた。先頭メンバーはログイン済みである。
この配置は、この操作が無ければ到達する手段が無いという本節の前提そのものである。

**確認できたこと:**

- **注記が出る条件**: 接続先を作っただけでは注記は出ず、**グループに追加した時点で
  出る**。これは仕様どおり（グループに属さない接続先は自動切替の対象ではないので
  警告しない。項目5 の裏返しにあたる）。グループ編集画面の候補一覧には出ない。
- **カードが切れていないこと（項目1 の一部）**: 画面 1920×1080、左右の余白 96 で
  コンテンツの右端は 1824。本体カードが `[96,616]–[1511,858]`、
  `初回ログイン` のカードが `[1535,616]–[1824,786]` で、**他のすべての行と同じ
  右端に収まっていた**。カードは `focused=true` を取れており D-pad で到達できる。
  幅の配り方も設計どおりで、本体カードが残り幅（1415px）、操作カードが実寸
  289px を確保している（`HomeScreen.kt` の `weight(1f)` の KDoc の理由）。
- **接続中から実行したときに、その接続先が起動すること（項目2 の一部）**:
  確認が1枚出たあと `tun0` が落ち、**7番目のメンバー**が起動した（先頭ではない）。
- **二度押しの窓が開いていないこと（項目3、接続済みの状態から）**: 試行が
  生きているあいだ、ホームの行は**画面構成に存在さえしていなかった**
  （ダイアログの窓が前面に出ているため）。`初回ログイン` のカードが戻ったのは
  試行が決着した区間であり、それより前には一度も戻っていない。
- **10秒規則が適用されていないこと（本節の存在理由）**: `promptUser()` 経由の
  ダイアログが **約43秒**立ち続けた。機械が始めた接続なら裁定30 の10秒規則と
  裁定95 の `cancelActiveDialog()` が10秒で畳む。畳まれたのは
  `connectTimeoutSec = 45` の期限どおりの時刻であり、**人が居るかどうかの判定では
  なく接続の期限**である（裁定78 が禁じているのは前者だけ）。
- **失敗後に巡回へ戻ること**: 試行の終了から約40秒後に先頭候補で自動的に
  繋ぎ直された。テスト用の接続先は以後選ばれない（安全策 S1）。

**確認できていないこと（この観測では届かなかった）:**

- **認証画面そのもの**: `test.invalid` は名前解決に失敗するので認証に到達せず、
  同じ `promptUser()` 経路で `ErrorDialog`（`OpenConnectManagementThread.errorAlert()`、
  ボタン1つ）が出た。**「ダイアログが10秒を超えて立つ」ことは確認できたが、
  それが認証画面である場合は確認していない。** 項目2・項目4 は実在するサーバと
  パスワード入力が必要で、**未実施**のまま。
- **`初回ログイン中 / 認証画面で入力してください（押し直し不要）` の表示**:
  試行中はダイアログの窓が前面にあり、ホームの行を観測できなかった。
  **カードが無いことは確認したが、この文言が出ていたことは確認していない。**
- **ダイアログを開いたまま →・決定を連打しても消えないこと**（項目3 の後半）:
  観測を汚さないため押していない。**未実施。**
- **確認の文面・初期フォーカス・`キャンセル`／BACK の挙動**（項目2 の前半）:
  ボタンが2つ出たことまでしか見ていない。**未実施。**
- **項目5（グループに属さない接続先）**: テスト用の接続先はグループに入れたので
  確認していない。**未実施。**
- **押した時点でメンバーが外れていた場合の拒否**（項目3 の末尾）: **未実施。**

**測り方の限界（1回目の観測）:** 画面の観測は `uiautomator dump` を約2.5秒間隔で
回したもので、「決着したからカードが戻った」と「2秒早く戻った」を**分離できて
いない**。より細かく見るには観測の間隔を詰める必要があるが、`uiautomator dump` を
速く回すと dump 側が落ちる（この観測中に1回落ちた）。

#### 9-3-2. 二度押しの窓の直接観測（2026-10-07、同じビルド）

**1回目の観測では、肝心の区間を1フレームも捉えていなかった。** 承認から
エラーダイアログが前面に出るまでが約2秒しかなく、観測の間隔より短かったためである。
**ダイアログが前面にあるあいだ、ホームの行は画面構成に存在しない**（別ウィンドウが
上に載る）ので、その間は二度押しのしようがない。**実際に露出しているのは、承認から
ダイアログが出るまでのダイヤル中だけ**である。

そこで接続先のサーバ URL を **`192.0.2.1:443`** に変えて測り直した。これは
RFC 5737 が文書用に予約したアドレスで、**どこにも到達しない。** 名前解決は要らず、
TCP の接続要求は応答が返らないまま宙に浮くので、**エラーダイアログが出ないまま
`connectTimeoutSec = 45` の期限まで「接続しようとしている」状態が続く。**
その間ホームの行が見えたままになる。**この節の確認をやり直す人は、即座に失敗する
名前（`test.invalid` など）ではなくこのアドレスを使うこと。**

VPN に接続した状態から実行し、画面を約2.5秒間隔で記録しながら、観測を汚さない
`→` `↑` `↓`（決定は押さない）を連打した。

| 時刻 | `tun0` | `初回ログイン` のカード | `初回ログイン中` の注記 |
|---|---|---|---|
| 21:12:42–45 | 1 | 有 | — |
| 21:12:45 | 1 | 有 | 確認ダイアログが開いている |
| 21:12:47 | **0** | **無** | **有** |
| 21:12:50 〜 21:13:26 | 0 | **無**（継続） | **有**（継続） |
| 21:13:34 | 0 | **有（戻った）** | — |

**確認できたこと:**

- **カードは47秒間ずっと消えていた。** 承認の直後（`tun0` が落ちた時刻）から
  期限まで、ナビゲーションキーを連打しても一度も現れない。**二度押しの窓は
  開いていない**（項目3 の前半は確認済みとする）。
- **`初回ログイン中 / 認証画面で入力してください（押し直し不要）` が実際に出ていた。**
  1回目の観測では見られなかった表示である。
- カードが戻った時刻は期限どおり。21:12:47 + 45秒 = 21:13:32 に対し観測は 21:13:34。
- 途中の3フレームで注記が消えていたが、これは**上下キーで画面がスクロールして
  行が画面外にあった**ためで、カードはどのフレームにも現れていない。
- そのうち1フレームにグループ行が写っており、
  `7 件の候補 ・ 自動切替 ON / 接続中 (テスト用)` と出ていた。
  **7番目の候補で繋ごうとしていたことが画面側からも裏付けられた。**

**項目3 の後半（ダイアログを開いたまま連打）について:** 上に書いたとおり、
ダイアログが前面にあるあいだホームの行は画面構成に存在しないので、**この確認は
書かれたままでは実行できない。** 守りは画面側の印ではなく**ウィンドウの構造**に
よる。認証ダイアログが出ている最中に行へ戻る経路（HOME キーで抜けて戻るなど）が
あるかは確認していない——`TvMainActivity.onResume` がダイアログを貼り直すので
戻った直後に上へ載るはずだが、その隙間は測っていない。**この1点は未実施のまま
残る。**

#### 9-3-3. 行内の D-pad（項目1 の残り。2026-10-07、同じビルド）

### 新しい判定が見ないもの（残る限界。**結果を読むときに必ず思い出すこと**）

仕様書 §3 の「新しく残る既知の限界」である。N-1〜N-5 が仮に全部通っても、次は**確認した
ことにならない**。

1. **遅延は良いのに帯域だけ細い回線は見えない。** 帯域制限やシェーピングを受けた経路は
   応答時間が健全なまま容量が低い。受動観測では測れない。N-2 の合格は「応答時間が悪い
   経路で切り替わる」ことを言うだけで、「遅い回線で切り替わる」とは言っていない。
2. **既定の `degradedRttMs = 250 ms` は万人向けではない。** 応答時間には、疎通確認の宛先
   までの距離が含まれる。宛先が遠い環境では、健全な経路でも中央値が 250 ms を超えうる
   （ばらつきの条件が同時に要るので、それだけでは発火しない）。**N-1〜N-5 の前に、その
   環境の健全な経路の応答時間を測って記録すること**（下の「共通の前提」）。この環境で
   通ったことは、別の環境で通ることを言わない。
3. **応答時間が悪い経路でも、利用者が見ているものは問題なく見えていることがある。**
   N-2 で「切り替わった」は、「見え方が良くなった」ではない。**切替の前後で画面に何が
   映っていたかを、別に記録すること。** 切替が見え方の改善と一致しなかった場合、
   それは N-2 の不合格ではなく、この限界の観測である（記録して残す）。

### 共通の前提と禁止事項（旧判定の走行で実際に時間を失った教訓を引き継ぐ）

**走らせる前に、毎回確かめる。**（旧 10-2〜10-6 の試行記録、10-3 の調査記録の教訓）

- **グループ行の状態を、走行の前後に必ず読む。** `tun` の存在は、エンジンが接続中と
  考えている証拠にならない（旧記録: トンネルは生きていたがエンジンは `Idle` だった）。
  `接続済み (…)`（＝`Healthy`）であることを、画面で確認してから始める。
- **繋がっている候補がグループの最後のメンバーでないこと**（N-4 を除く）。前へ進む切替は
  折り返さない（`docs/DECISIONS.md` 項目14）。
- **安全策 S1 の除外集合が空であること。** 画面に出ないので、**利用者の明示的な接続を
  1回行ってから**始める（その接続が除外集合と一周の記録をクリアする）。
- **設定を先に済ませる。** 設定の保存は一周の記録を消す。走行の途中で設定を触らない。
- **認証ダイアログが出たら、利用者本人が画面で答える。** ユーザー名・パスワード・証明書の
  扱いを、手順書・記録・チャットのどこにも書かない／貼らない。この節の手順は、資格情報を
  読む・書く・共有する操作を一切含まない。

**測定の道具。**

- **切替の検出は `/proc/net/dev` のカウンタの後退で行う。** 正常な切断ではインターフェース
  名が再利用されるので、名前の変化では見落とす（旧記録）。また異常があった端末では古い
  `tun` が `DOWN` のまま残り、生きているのは `tun0` とは限らない。**全 `tun*` の行を
  記録すること**:

  ```
  # 端末側で動かし、UI には触らない。出力は手元のファイルへ（走行の前後でグループ行を別に読む）
  adb shell 'while :; do echo "== $(date +%T)"; grep " tun" /proc/net/dev; sleep 10; done' > run.log
  ```

  どの `tun` の行でも、累計が前の行より**減る**か、新しい名前の行が現れて伸び始めたら
  切替（または張り直し）である。
- **窓ごとの受信速度は、自分で計算して「帯の内側か」を確認する。** アプリと同じ式
  （窓の最古と最新の累計バイトの差 × 8 ÷ 経過ミリ秒 = kbps）を、60秒の窓について出す。
  **帯は既定で 50 kbps より上・1000 kbps より下**。確認できない走行は「発火しなかった」
  としか読めない。
- **応答時間の独立な測定。** `adb shell ping -c 20 <疎通確認の宛先>` で、トンネル越しの
  往復を測る（中央値と、最大 − 最小）。**これは ICMP であり、アプリが測る TCP 接続の
  時間と同じではない**（代用の計測である）。端末に TCP の接続時間を直接測れる道具が
  あれば、そちらを優先する。食い違いがあれば、食い違い自体を記録する。**N-1 の走行中は
  流さない**（観測が待機状態を壊す。走行の前と後に測る）。
- **画面の観測。** グループ行のスクリーンショットを撮る（`screencap`）。**`uiautomator dump`
  を連続して回さない**（旧記録: 12分間 5 秒ごとに回したあとフォーカスが復帰しなくなった。
  製品の不具合か計測の副作用かは区別できていない）。画面記録の間隔は 5 秒より詰めない。

**やってはいけないこと。**（旧記録で実害が出たもの）

- `am force-stop` を使わない（アプリごと落ちて VPN が10分以上切れた）。
- **接続・切断を短時間に繰り返さない。** 提供元の接続制限に触れて認証が失敗した。**走行は
  1回を長く取り、走行の間隔を空ける。** 認証ダイアログが出たら BACK で閉じ（OK は押さない）、
  20〜30分置く。

**試験用の値と、元に戻すこと。** 設定画面の値（疎通確認の宛先、各しきい値）を試験のために
変えたときは、**走行の前に元の値を控え、終わったら利用者が戻す**。控えた値をこの文書に
書き込まない。到達しない宛先が要る場合は、RFC 5737 の文書用アドレス `192.0.2.1` を使う。

**記録の書式（各走行で埋める）。** 日時 ／ ビルド（`git rev-parse --short HEAD` と、
`adb shell pm path` ＋ `md5sum` で端末の APK が手元のビルドと同一であること）／ 設定値の
全部 ／ 繋がっている候補の位置 ／ 事前の応答時間（中央値・最大 − 最小・サンプル数）／
窓ごとの受信 kbps ／ 切替の時刻 ／ グループ行の文言 ／ 合否と、**合格に読んでよい根拠**。

### N-1. 待機中に切り替わらない（**この改訂の合否を決める項目**）— △ **限定的な結果（2026-10-10 00:14〜00:26 実機）**

**なぜこれが決め手か。** 古い判定は、まさにこの場面（誰も何も見ていない待機中）で
誤判定して、7分半で候補を歩き切った（10-5-1）。判定の根拠を変えた理由は、これを直す
ことである。**ここが通らなければ、改訂は目的を果たしていない。**

**前提。** ON。設定は**既定値のまま**（往復 250 ms / ばらつき 150 ms / 受信の下限 50 kbps /
上限 1000 kbps / 再開しない）。共通の前提を満たす。**グループの途中の候補**につなぐ。
設定画面の導出文が「受信が 50 kbps を下回っているあいだは判定しません（待機中は
切り替わりません）」と出ていることを、走行の前に目で見る。

**手順。**

1. 走行の前に、トンネル越しの応答時間を測る（`ping`。中央値・最大 − 最小を記録）。
2. グループ行が `接続済み (…)` であることを画面で確認し、記録を始める（`run.log`、
   5 秒より粗い間隔の画面記録）。
3. **何も再生せず、観測側は一切通信を起こさない**（`/proc/net/dev` を読むことと
   スクリーンショットだけ）。**7分半以上**放置する（古い判定が誤判定した走行は453秒）。
   **端末自身のバックグラウンド通信のバーストを含む時間帯を狙う**——古い誤判定は、
   バースト（最大 6.3 Mbps）の前後に生まれた。
4. 走行の後に、もう一度 `ping` を測り、グループ行を読む。

**観測すること。** 切替が起きたか（カウンタの後退・張り直し）／グループ行の文言（切替前後で
同じ接続先か、「直前の切替」が出ていないか）／**60秒の窓ごとの受信 kbps と、そのうち
「受信 50 kbps 以下」「帯の内側（50 超 1000 未満）」の窓の数**／バーストの有無（最大受信）。

**合格。** 走行の全期間で**切替が 0 回**で、グループ行が前後で同じ。

**不合格。** 切替が1回でも起きた。**そのときの窓ごとの値（受信・送信・直前の応答時間）を
必ず残す**——閾値の位置の問題か、測り方の問題かを切り分ける材料になる
（`docs/DECISIONS.md` 項目17 の「再開の入口」）。

**合格を読むときの条件（ここを省くと過大評価する）。**

- **受信 50 kbps 以下の窓しか無かった走行は、下限（待機中を弾く条件）が働いたことしか
  言わない。** 応答時間の2条件が待機中の窓を守っているか——つまり**受信の下限が無くても
  守られるか**——は、**帯の内側の窓**（バーストの前後の「受信は細いが 50 kbps を超える」窓。
  旧記録では受信 689 kbps の窓があった）があって初めて試される。帯の内側の窓が1つも
  無かった走行は「**下限だけを確認した。応答時間の条件は待機中に対して試されて
  いない**」と書く。バーストが無かった走行は、後日繰り返す。
- 1回の合格は、別の時間帯・別の端末の挙動を言わない（旧記録の失敗窓は 30 窓中 4 窓、
  1回の走行の中の約13%だった）。

#### N-1 の実機記録（2026-10-10 00:14〜00:26。**限定的。合格とは書かない**）

**環境。** `versionCode 1122`（コードの最終コミットは `50c3835`）。機能 **ON**・設定は既定値。
走行前に導出文が「受信が 50 kbps を下回っているあいだは判定しません（待機中は切り替わりません）」と
出ていることを画面で確認した。繋いだのは**グループの途中の候補**（6件のうち3番目）。
**何も再生せず、観測はトンネルを通らない経路（adb/LAN）だけで行った。** 標本は20秒間隔・29点。

**結果（事実）。**

| 観測 | 値 |
|---|---|
| **経路品質起因の切替** | **0回**（「直前の切替」の表示が走行中**1度も出なかった**） |
| 死活起因の切替 | **1回**（00:22:55 ごろ。3番目→4番目の候補。理由表示なし） |
| 受信の最大（20秒区間） | **27.41 kbps** |
| 受信が 50 kbps を超えた区間 | **0 / 27** |
| **帯の内側（50超1000未満）の区間** | **0** |
| 走行前の応答時間（ping、3番目の候補） | 中央値 約894 ms ／ ばらつき 648 ms ／ **損失 66%** |
| 走行後の応答時間（ping、4番目の候補） | 平均 1596 ms ／ 最小309・最大3267（ばらつき 2958 ms）／ 損失 0% |

**なぜ「合格」と書かないか。** 手順の「合格を読むときの条件」に自分で書いたとおりである。
**受信が 50 kbps を超えた窓が1つも無かった**（最大 27.41 kbps）。したがってこの走行が
示したのは**下限（待機中を弾く条件）が働いたこと**だけであり、
**応答時間の2条件が待機中の窓を守るかどうかは、一度も試されていない。**
旧判定が壊れた走行には受信 689 kbps の窓があった。今回はバーストが無かったので、
**後日、バーストを含む時間帯で繰り返す必要がある。**

**さらに重要: この走行では、応答時間の2条件は最初から成立していた。**
ping の値（中央値894 ms・ばらつき648 ms、走行後の候補では ばらつき2958 ms）は
いずれも閾値（250 ms / 150 ms）を大きく超えている。つまり
**切替を止めていたのは受信の下限だけ**であり、もしバーストで受信が帯の内側に入っていれば
**この機能は切り替えていた**。そしてその切替は——経路が実際に劣化しているのだから——
**誤判定ではなく正しい動作**である。

#### N-1 の手順そのものの欠陥（この走行で判明。次に走らせる人のために直す）

1. **前提に「経路の応答時間が閾値を満たしていないこと」が無い。**
   手順は合格を「切替が0回」と定めているが、**経路が本当に劣化していれば切替は正しい動作**
   であり、その条件では**正しい動作を不合格と読んでしまう。**
   N-1b の説明には「経路が健全なので」と書いてあるのに、N-1 の前提には落ちていた。
   **走行前の ping で閾値を超えていたら、その候補で N-1 を走らせても判定にならない。**
2. **合格条件が死活起因の切替を区別していない。** 今回まさに死活起因の切替が1回起きた。
   数えるべきは**経路品質起因の切替だけ**である。区別は画面で読める——
   「直前の切替: 経路品質で切替」は経路品質起因のときだけ出て、`FailingOver` の数秒より
   長く残る（裁定R19）。**この表示の有無を合格条件に書くこと。**
3. **ping はアプリが測っているものではない。アプリと同じものを測る手段がある。**
   アプリは**`ProbeTarget` への TCP 接続**の所要時間を測る。ping（ICMP）は別物で、
   今回の経路は **ICMP を 66% 落としながらアプリは `接続済み` を保っていた**。

   > **2026-10-10 訂正。** ここに最初「端末に `nc`・`curl` が無く TCP 接続時間を
   > 直接測る手が無い」と書いたが**誤りだった**。`nc` 単体は無いが、
   > **`toybox nc` が使える**（`toybox nc IPADDR PORT`。**ホスト名は解決しないので
   > IP を渡すこと**）。所要時間は端末の `date` に `%N` が無いので**PC 側で計る**。
   >
   > ```
   > # PC 側。rc=0 が成功。adb 往復ぶん数十 ms 上乗せされる
   > for i in 1 2 3 4 5 6; do
   >   S=$(date +%s%3N)
   >   RC=$(adb shell 'timeout 6 toybox nc -w 5 1.1.1.1 443 </dev/null >/dev/null 2>&1; echo $?')
   >   E=$(date +%s%3N); echo "$i rc=$RC $((E-S))ms"
   > done
   > ```
   >
   > **これが N-1・N-2 の前提を確かめる正しい道具である。** ping ではなくこれを使うこと。

4. **走行中は画面を消さないこと（裁定44）。** 画面消灯で VPN を切断するのは設計である
   （`FailoverService.kt:227`）。**端末が寝ると走行はそこで終わる。**
   2026-10-10 の走行は、観測者が端末から離れた約10分後に TV がスリープし、
   トンネルが消えた。そのあとの測定値（TCP 接続が全失敗）は**寝ている端末を測った
   だけで無意味**だった。走行の記録には**毎回 `dumpsys power` の `mWakefulness` を残すこと。**
   スリープ時間を延ばすのは端末の設定変更なので、**自動化で勝手に変えないこと。**

**後片付け。** 機能を **OFF**（既定値）に戻して保存した。接続はそのまま、
疎通確認の設定も元のまま（`1.1.1.1` / `443` / 30秒 / 3回）。

**任意の追加（N-1 が合格したあと）: N-1b。** 受信の下限を `0`（下限なし）にして同じ走行を
する。経路が健全なので、応答時間の条件だけで切り替わらないはずである。**不合格（切り替わる）
なら、待機中を守っているのは下限だけ**だということで、下限を `0` にした利用者の状況を
説明する材料になる。**誤判定を起こしうる設定を意図して作る走行なので、候補を歩き切る
可能性と、提供元の接続制限を覚悟のうえで、N-1 の合格後に1回だけ行う。** 終わったら下限を
元に戻す。

### N-2. 経路が悪いと切り替わり、理由が画面に出る（**未実施**）

**前提。** ON。共通の前提を満たす。**応答時間とばらつきを、独立に測って条件を作る**。
旧手順の `ping -s 1400 -i 1` は**流用できない**——往復それぞれ約 11 kbps で、受信が
新しい判定の下限 50 kbps に届かない（旧手順は送信を需要の代用に使うための通信だった）。

**条件を作る。** 次の3つを**同時に**満たす状態を作り、**それぞれを走行の前に測って確認する**。

- 応答時間の中央値 > `degradedRttMs`、かつ最大 − 最小 > `degradedJitterMs`。
  作り方は2つ。(a) **旧仕様 §2-2 で遅かった候補**につなぐ（平均 137〜379 ms、mdev
  140〜336 ms と実測された）。**平均が 250 ms を下回る走行もありうる**ので、事前の `ping` で
  中央値が `degradedRttMs` を超えているかを確かめ、超えていなければ `degradedRttMs` を
  下げる（**下げたことを記録し、既定値での確認とは区別する**）。(b) 端末の上流（ルータや、
  端末を通す PC）で遅延とゆらぎを足す（例: Linux の `tc qdisc add dev <iface> root netem
  delay 300ms 150ms`）。トンネルの外側に足すので全候補に同じように効く。
- 受信が帯の内側（50 kbps 超・`slowRxKbps` 未満）。実際のストリームの再生で作るのが
  確実で、ビットレートが高ければ `slowRxKbps`（最大 5000）を上げる。**窓ごとの受信を
  計算して確認する。**

**手順。**

1. 条件を事前に測って記録する。グループ行が `接続済み (…)` であることを確認する。
2. 接続（`Healthy`）に戻った時刻を起点に、`run.log` とグループ行の画面記録を取る。
   **画面記録は 5 秒間隔にする**（次の「疎通確認中」の観測のため）。
3. 切替を待つ。切替のたびに、新しい候補で `疎通確認中` が**約15秒**出てから `接続済み` に
   なるのを見る。

**観測すること。** 接続からの経過時間 ／ 切替の時刻（カウンタの後退）／グループ行の
文言（`直前の切替: 経路品質で切替` が出るか。**前へ進んだ切替と、一周の終わりに最良へ
戻る切替は、この文言では区別されない**ので、切替の列は**接続先の名前の変化**で読むこと
（`docs/DECISIONS.md` 項目11）／新しい候補で
`疎通確認中` を経由したか／**切替の前後に画面に映っていたもの**（限界3）。

**合格。** 条件を3つとも事前に独立に確認したうえで、**トンネルが上がってから約60秒以降
〜3分以内に1回以上切り替わり**、グループ行に `直前の切替: 経路品質で切替` が出て、
**新しい候補が `疎通確認中` を経てから `接続済み` になった。**
（窓が60秒で、接続直後の猶予が15秒、疎通確認の周期が30秒なので、60秒より前の切替は
古い証拠の持ち越しを疑う。「3分」は筆者の目安で、仕様から導いた値ではない。）

**不合格。** 条件を3つとも確認できているのに、3分以上切り替わらない。または**約60秒より前に
切り替わった**／**`疎通確認中` を一度も経ずに `接続済み` になった候補があった**（猶予を
飛ばして昇格した疑い。`docs/DECISIONS.md` 項目20）。

**判定不能（合否を付けない）。** 条件の一つでも確認できなかった／前提（最後のメンバー、
除外集合、グループ行の状態）を満たさなかった。**「切り替わらなかった」という記録だけが
残る**——旧記録の 10-2〜10-6 の試行は、これで判定を下せなかった。`ping`（ICMP）と
アプリの測る TCP 接続時間が食い違っている可能性は、ここで初めて疑う。

### N-3. 経路が健全なら、受信が帯の内側でも切り替わらない（**未実施**）

**なぜ。** 仕様書 §3 の表の1行目「低ビットレート再生を遅いと誤判定する」を絞れると
主張している。古い判定は、受信が低いだけで発火した（`docs/DECISIONS.md` 項目5）。
**この主張が実機で通るかは未確認**である。

**前提。** ON。既定値。**経路が健全**（事前の `ping` で中央値 ≪ 250 ms、最大 − 最小 ≪ 150 ms）。
**受信が帯の内側**になる通信を5分以上流す——低ビットレートの再生（音声のみ、低画質の動画）が
実際の利用に近い。窓ごとの受信を計算して、帯の内側の窓が大半であることを確認する。

**手順。** 共通の前提を満たし、`run.log` を取りながら、通信を5分以上続ける。走行の後に
もう一度 `ping` を測り、経路が健全なままだったことを確かめる。

**合格。** 経路が健全なまま（事前・事後の測定）、帯の内側の窓が複数ある走行で、**切替が
0 回**。**不合格。** 切替が起きた（そのときの窓ごとの値を残す）。**判定不能。** 走行中に
経路の応答時間が劣化していた（事後の `ping` が悪い）、または帯の内側の窓が無かった。

戻った／最後のメンバーに、測定上は他の候補が明確に良いのに居座った。

**この走行が示したこと（最も重要）。**

### 【旧判定】修正前に残っていた確認（2026-10-08 時点。**歴史として残す**）

**それでも実機での確認は済んでいない。** 理由を2つとも残す。

**1. 「生きているのが `tun0` 以外」の状況を狙って作れなかった。**

### 【旧判定】10-2〜10-6 の試行記録（2026-10-08 昼。**判定は得られていない**）

走らせたが、**どれも「切り替わった／切り替わらない」の判定を下せる状態ではなかった。**
「切り替わらなかった」という記録は残ったが、**条件下で切り替わらなかったとは言えない。**
やり方ごと残しておく——同じ失敗を繰り返さないためである。

**作った条件:** 「速度低下で切り替える」を ON、受信速度の下限を**上限の 5000 kbps**
まで上げ、`adb shell ping -s 1400 -i 1 1.1.1.1` で往復それぞれ約 11 kbps の通信を
トンネルに流した。受信は閾値を大きく下回り、送信は `demandTxKbps = 5` を大きく上回る。
**本物の遅い回線を待たずに条件を作れる**（ただしこれは機構を試すだけで、仕様書 2-1 の
ばらつく 424 kbps の候補で窓平均の規則が成立するか——裁定R20 の本題——は試せない）。

**試行1（待機、約7分）:** 切替は起きなかった。ただし偶然 Fire TV が裏で約6MB を
落としており、**切替条件を満たした60秒窓が10個連続で成立していた**（受信
145〜838 kbps、送信 14〜247 kbps）。つまり「待機中だから条件を満たさなかった」のでは
なく、**条件を満たしたのに切り替わらなかった。** 判定不能。
なお**本当に待機しているときの通信は受信・送信とも 0.1〜1.1 kbps** で、
送信側の閾値 5 kbps の 5〜50 分の1 である（節 10-5 の誤判定の心配は、少なくとも
この環境では送信側の条件が効いて成立しにくい、という材料にはなる）。

**試行2（ON・下限 5000・ping、12分）:** 切替は起きなかった。`tun0` のカウンタは
12分間単調増加で張り直しも無し。**しかしこのとき繋がっていた候補は添字1で、
そこへ至った経路は死活判定による切替だった。** 添字2以降が安全策 S1 の除外集合に
入っていれば `onSlowLinkSwitch` の `nextStartableIndex(...) == null` の門で止まる。
除外集合はメモリ上にあり画面に出ないので、**前提を確かめられなかった。** 判定不能。

**試行3（前提を揃えてやり直し）:** 利用者の明示的な接続（`onUserConnect`）で
除外集合と一周の記録をクリアし、添字0から始めた。**ここで VPN が戻らなくなり、
データが取れなかった。** 原因は観測側の操作である（下記）。

**次に行う人への前提（これを確かめずに走らせても無駄になる）:**

1. **繋がっている候補がグループの最後のメンバーでないこと。** 速度起因の切替は
   折り返さないので、最後のメンバーでは構造的に発火しない（`docs/DECISIONS.md` 項目14）。
2. **安全策 S1 の除外集合が空であること。** 画面に出ないので、**利用者の明示的な接続を
   1回行ってから**始めるのが唯一の確実な方法である（`onUserConnect` がクリアする）。
3. **一周の記録が空であること。** 設定の保存でも利用者の接続でもクリアされる。
4. 判定には**窓の 60 秒**が必要で、`graceAfterConnectSec = 15` も先に過ぎている必要がある。

**やってはいけない観測方法（2026-10-08 に実害が出たもの）:**

- **`am force-stop` を使わない。** フォーカスの復帰のために使ったが、アプリごと落ちて
  **VPN が10分以上切れ**、繋ぎ直しの巡回で認証が失敗した。画面を作り直すだけなら
  `am start` で足りる。
- **`uiautomator dump` を5秒ごとに回さない。** 12分間続けたあと**どの D-pad キーでも
  フォーカスが復帰しない状態**になった（`focused="true"` がゼロ）。製品の不具合か
  計測の副作用か**区別できていない**——`uiautomator` は UiAutomation サービスを繋ぐので
  アクセシビリティフォーカスを乱しうる。切替の検出は `/proc/net/dev` の `tun0` の
  **カウンタ後退**で足りる（端末側のループで済み、UI に触らない）。
- **短時間に接続・切断を繰り返さない。** 試行のあと
  `Login failed. Please enter your password.` の認証ダイアログが出た。提供元の
  接続制限に触れた可能性がある。**この節の確認は1回の走行を長く取り、走行の間隔を空ける。**
  このダイアログは BACK で閉じ（**OK は押さない**——拒否された認証情報の再送になる）、
  **約20分後にバックオフを経て自力で回復した**（12:15 に中断、12:35 と 12:36 に
  2つの接続先で認証成功）。保存済みの認証情報は無効になっていなかった。
  **一時的な制限である**という見立ての裏づけであり、同じ症状が出たら
  まず20〜30分置くこと。

## 12. 計測に使った道具（再現の補助）

利用者が画面を見て確認する分にはリモコンだけで足りる。開発時に使った計測手段を参考に残す。

- `adb shell uiautomator dump` — フォーカス矩形と、画面に実際に描かれている文字の一覧。
  「ボタンが画面外に落ちている」類の欠陥はこれで検出した。
- `adb shell dumpsys window` — IME ウィンドウの `mViewVisibility` / `mHasSurface`。
  **ソフトキーボードが出ているかの判定はこれで行う**（`screencap` は IME レイヤを含まない）。
- `adb shell sendevent /dev/input/event4 …` — 本物のリモコンと同じキー経路。
  `adb shell input keyevent` は IME に届かない。選択キーは **`KEY_KPENTER` (96)**。
- `adb logcat -s FailoverService:D` — 画面の消灯・点灯、プロセス kill からの復帰、
  wake lock の取得・解放。
- **`uiautomator dump` を繰り返して座標だけを時系列に記録する**（節 9-3-1 で使用）。
  `clickable="true"` のノードの矩形を1行1時刻で並べると、カードの出現・消失と
  画面の入れ替わりが目で追わずに追跡できる。**間隔は2秒以上空けること**: 速く回すと
  `UiAutomationService ... already registered!` で dump 側が落ちる（節 9-3-1 の
  観測中に1回落ちた）。文字は Windows の端末を経由すると化けるので、
  `adb shell cat` の出力はファイルへ落として UTF-8 で読むこと。
- `adb shell pm path <pkg>` と `md5sum` の照合 — **端末に入っている APK が手元の
  ビルドと同一か**を確かめる。「直したのに直っていない」の大半はここで切り分けられる。
- 初回ログインの判定の入力を見るとき: プロファイルの prefs で `FORMDATA-` で始まる
  **キーの個数だけ**を数える。**値は読まないこと**（認証情報である）。
- **「認証が通っているか」はカウンタで確かめられる。値に触る必要は無い。**
  プロファイルの prefs に `attempt` / `connect` / `cancel` と、それぞれの `_prev`
  （最後に起きた時刻、epoch ミリ秒）がある（`OpenConnectManagementThread.updateStatPref`）。
  意味は次のとおりで、**`connect_prev` が `cancel_prev` より新しければ直近の認証は
  通っている。**
  - `attempt` — 接続試行の開始ごと（`runVPN()` の先頭）
  - `connect` — `STATE_CONNECTED` に到達＝**認証が通ってトンネルが張れた**
  - `cancel` — 認証を**諦めた**とき（`User canceled auth dialog`、証明書拒否、
    切断要求）。**サーバに拒否されたことを意味しない**ので、
    「`Login failed` が出た」と「`cancel` が増えた」は別物である
  実際に接続している相手は `/proc/net/tcp` の ESTABLISHED な行（アプリの uid）で
  確かめられる。画面の候補名と突き合わせると、表示が実態と合っているかも分かる。
