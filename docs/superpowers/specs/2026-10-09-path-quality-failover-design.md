# 経路品質の低下による接続先の切り替え（設計・改訂版）

**これは `2026-09-27-throughput-failover-design.md` の §4-2（判定）を置き換える。**
旧仕様の他の節（候補の選び方、一周で止める、安全策との関係）はそのまま生きている。

**改訂の理由: 旧仕様の判定は実機で成立しなかった。** 記録は
`docs/MANUAL-TEST.md` 節 10-5-1 と `docs/DECISIONS.md` 項目17 にある。

---

## 1. 何が成立しなかったのか

旧仕様 §4-2 は次の両方を窓（60秒）の平均で見ていた。

```
受信速度 < slowRxKbps      既定 1000 kbps
送信速度 > demandTxKbps    既定 5 kbps     ← 「誰かが使おうとしている」の代用
```

**2026-10-09 の実機観測（7分半、観測側は通信を一切起こしていない）:**

| | |
|---|---|
| 条件を満たした60秒窓 | **4 / 30** |
| その窓の値 | 受信 **5 / 5 / 5 / 689** kbps、送信 **86 / 86 / 88 / 97** kbps |
| 結果 | 速度起因の切替が候補を添字1 から添字5 まで**歩き切った** |

端末自身のバックグラウンド通信（最大 6.3 Mbps）の前後に「受信が細く送信が太い」
区間が生まれ、両条件がそろった。**誰も何も見ていない。**

### 根本原因（閾値の問題ではない）

```
観測される受信速度 = min(回線の容量, 誰かが要求している量)
```

**受動観測はこの2つを分離できない。** 受信が低く見えたとき、それが「回線が細い」
のか「誰も要求していない」のかが原理的に分からない。送信速度を需要の代用に
したのはこの分離の試みだが、**上り主体の通信で崩れる**（受信 5 / 送信 86 kbps）。

**閾値をどう動かしても解けない。**

- `demandTxKbps` を上げる: 観測された送信は 86〜97 kbps なので 5→50 でも成立する。
  かつ旧仕様 §6-4 と `DECISIONS` 項目1 のとおり、上げると対象の 424 kbps の候補で
  発火しなくなる（遅い候補の送信は受信への ACK が主で、受信に比例して下がる）
- `slowRxKbps` を下げる: 今日の窓4 は**受信 689 kbps の本物のダウンロード**だった。
  裏で走る 1 Mbps 未満の通信は、どの閾値でも「遅い回線」と区別できない

## 2. 何を測るか（改訂の核心）

**プローブの応答時間と、そのばらつきを主たる根拠にする。受信速度は補助の門に降ごす。**

### なぜ応答時間なのか

**需要に依存しない。** 誰も何も落としていなくても測れる。これが旧仕様の
分離できない問題を回避する唯一の受動的な道である。

**旧仕様 §2-2 が既に分離を示している**（同じ端末・同じ時間帯）。

| 経路 | min | avg | max | mdev |
|---|---|---|---|---|
| VPN あり（遅い候補A）4回平均 | 81〜84 | 137〜379 | 556〜1067 | **140〜336** |
| **VPN なし（素の回線）** | 69.8 | **73.5** | 83.3 | **5.0** |

**遅い候補は遅延のばらつきに桁で出ている。** 一方 2026-10-09 の誤判定が起きた
ときは裏で 6.3 Mbps 出ており、**経路は健全だった**。応答時間は
「回線が本当に悪い」と「回線は良いが誰も落としていない」を分けられる。

> **旧仕様 §6 の末尾は「4 と 5 はプローブの応答時間では見分けられない」と
> 書いているが、これは誤りである。** 項目4・5 が言う「受信が少ない理由」は、
> 応答時間が健全なら「遅いからではない」と判断できる。旧仕様はこの可能性を
> 検討せずに退けていた。

### 測り方（追加の宛先を作らない）

**既存の死活プローブをそのまま使う。** いま `TcpHealthProbe` は
`ProbeTarget`（既定 `1.1.1.1:443`）へ TCP 接続して真偽値だけを返している。

- **1回のプローブ周期で接続を3回行い、所要時間を記録する。** 逐次で、各回の上限は
  既存の `probeTimeoutMs`（既定 5000ms）。**新しい宛先も新しい権限も要らない。**
  通信量は TCP 接続3本ぶんで、旧仕様の「追加の通信は行いません」の精神を保つ
- **なぜ3回か。** 30秒間隔のプローブでは60秒の窓にサンプルが2個しか入らず、
  ばらつきを見るには足りない。旧仕様 §2-2 は ping 10発で測っていた。
  周期内で3回取れば**その周期のばらつき**が得られ、窓をまたぐ必要が無い。
  3は「ばらつきが見える最小」として選ぶ（2では中央値が定まらない）
- **死活判定の意味は変えない。** 3回のうち**1回でも成功すれば到達可能**とする。
  これは現在の「1回成功すれば可」と同じ強さであり、**安全策 S2 や裁定33 の
  期限の前後関係を動かさない**。失敗回数の数え方（`failureThreshold`）も変えない

### 判定

窓（既定60秒）について、次の**すべて**が成立したとき「遅い」とする。
応答時間のサンプルは、窓に入るプローブ周期の**全サンプルをまとめて**扱う
（1周期3回・30秒間隔なので、60秒の窓でおよそ6サンプル）。

```
応答時間の中央値     > degradedRttMs      既定  250 ms
応答時間の最大−最小  > degradedJitterMs   既定  150 ms
rxFloorKbps < 受信速度（窓の平均） < slowRxKbps    既定 50 〜 1000 kbps
```

- **応答時間の2条件が本体である。** 中央値だけでは地理的に遠い宛先と区別できず、
  ばらつきだけでは一過性の揺れを拾う。**両方を要求する**
- **送信速度の条件（`demandTxKbps`）は削除する。** 需要の代用として成立しない
  ことが実機で示された（§1）。`DECISIONS` 項目1 の「上げてはならない」は
  「この軸に解が無い」という形で引き継ぐ
- **代わりに受信に下限（`rxFloorKbps`）を置く。** 需要の信号を捨てるのではなく、
  **壊れていない形に置き換える**。意味は「**データは流れているが遅い**」である。

  > **この下限が無いと、改訂版は別経路で同じ失敗をする。** 送信の条件だけを
  > 削除すると「受信も送信もほぼ0（＝待機中）だが経路の応答時間が悪い」場合に
  > 発火し、誰も見ていないのに切り替わる。2026-10-09 の待機中の実測は
  > 受信 0.16 kbps（中央）であり、既定 50 kbps で確実に弾ける。
  >
  > **上限と下限を同じ式に書くこと。** 片方だけを別の節に離すと、将来どちらかが
  > 独立に動かされて帯が崩れる。
- **判定が「受信速度」単独で成立することは無い。** 旧仕様では受信と送信の2条件
  だけで発火したが、改訂版では**経路の応答時間が必ず要る**
- 接続直後は `graceAfterConnectSec`（既定15秒）のあいだ判定しない（据え置き）。
  **ただし `Connected` の再通知で猶予が延びてはならない**（`DECISIONS` 項目16）
- **失敗したプローブも所要時間を数えるが、数えるのは「実測した経過時間」である。**
  間欠的にタイムアウトする経路は実際に劣化しており、その事実を捨てる理由が無い。
  タイムアウトは自然に `probeTimeoutMs` 前後を計るので、劣化はそのまま乗る。

  > **タイムアウト値で埋めないこと（初稿の誤り）。** 初稿は失敗した回を
  > `max(実測, probeTimeoutMs)` として記録するとしていた。**接続拒否や
  > 名前解決の失敗は数ミリ秒で返る**ので、それを 5000ms の遅延として
  > 記録するのは事実に反する。**拒否は「遅い」ではなく「届かない」**であり、
  > それは `reachable` と既存の `failureThreshold` が扱う。
  > 実測をそのまま使えば、タイムアウトだけが大きな値として乗る。

  **全回失敗した周期は死活側の「到達不能」**であり、そのときは速度の判定ではなく
  既存の `failureThreshold` の数え上げが先に効く

### 既定値の根拠

旧仕様 §2-2 の実測から取る。素の回線が avg 73.5ms / mdev 5.0ms、遅い候補が
avg 137〜379ms / mdev 140〜336ms なので、**その間に線を引く**。

- `degradedRttMs = 250`: 素の 73.5 の3倍強、遅い候補の下限 137 より上。
  地理的に遠い宛先では常時超えうるので**利用者が変えられること**
- `degradedJitterMs = 150`: 素の mdev 5.0 とは2桁離れ、遅い候補の 140〜336 に入る。
  max−min は mdev より大きく出るので、この値は控えめな側である
- `rxFloorKbps = 50`: 2026-10-09 の待機中の実測（受信 中央 0.16 kbps）を確実に
  弾き、旧仕様 §2-1 の対象候補（424 kbps）を確実に通す位置。**下げると待機中の
  誤判定が戻り、上げると対象の候補を取りこぼす**

**既定値は出発点に過ぎない。** この実測は1台の端末・1つの宛先・1つの時間帯の
ものなので（§3-2 の限界）、**4項目すべてを利用者が変更できるようにする。**
範囲・刻み・意味・動かしたときに何が起きるかは **§4-A** にまとめた。

## 2-A. 一周したあとの行先（旧仕様 §4-5 への追加）

旧仕様 §4-5 は「一周したら速度による切替を停止する」と書いているが、**どこで
停止するかを書いていない。** 実装は前方にしか進まず折り返さないので
（`DECISIONS` 項目14）、**結果として最後のメンバーに居座る。**
2026-10-09 の実機でもそうなった（添字1 → … → 添字5 で停止、以後動かない）。

**これは弱点である。** 最後のメンバーは「良いから」ではなく「最後だから」
選ばれている。グループの順序は画面に「上が優先」と書いてある**利用者が宣言した
優先順位**なので、**最も優先度の低い接続先に置き去りにしている。**
しかもそこでは次候補が無く、速度起因の切替が無効になる。

### 決めたこと: 一周の終わりに、応答時間が最良だった候補へ戻す

**応答時間は需要に依存しないので、候補をまたいで比較できる。** これが旧仕様の
受信速度では成立しなかったことである（受信速度は `min(容量, 需要)` なので、
候補A を 4 Mbps の動画視聴中に測り候補E を音声のみで測れば、比較しているのは
需要であって候補の良し悪しではない。**窓を長くしてもこの交絡は消えない**）。

- **一周のあいだ、候補ごとに応答時間のサンプルを記録する。** 記録はメモリ上だけで、
  一周の記録（`slowLinkLaps`）と同じ寿命を持つ。**永続化しない**
- **検知の窓（60秒）は長くしない。** 検知の窓と比較の記録は別物である。
  各候補は一周のあいだ約60〜65秒保持されるので（2026-10-09 の実測と一致）、
  プローブ30秒間隔ならその候補について2周期ぶんが得られる
- **1周期の採取を3回から5回に増やす。** 2周期で**候補あたり10サンプル**になり、
  旧仕様 §2-2 が ping 10発で測ったのと同じ密度になる。TCP 接続が30秒あたり
  5本に増えるだけで、**窓を長くして一周を15分に伸ばすより桁違いに安い**
- **順位付け（2段で決める。1対1の比較を並べないこと）**:
  1. **最小の中央値を求める。**
  2. **中央値がそれから `degradedJitterMs` 未満しか離れていない候補を「同等」と
     見なし**、その中で**ばらつき（最大−最小）が最小**のものを採る。
  3. それも同じなら**グループの順序で先の方**を採る。

  新しい定数を導入しないこと——「有意に違うか」の尺度は既に `degradedJitterMs` が
  与えている。

  > **なぜ2段なのか（初稿の誤りの記録）。** 初稿は「中央値の差が許容未満なら
  > ばらつきで比べる」という**1対1の比較規則**を書き、それを線形走査で使って
  > 最良を選ぶつもりだった。**その規則は推移的ではない。** 許容幅150 で
  > `a(中央値300, ばらつき0)` / `b(200, 10)` / `c(100, 20)` を比べると
  > a>b（差100・ばらつき0<10）、b>c（差100・ばらつき10<20）、
  > c>a（差200≥150・中央値100<300）となり**循環する**ので、
  > 結果が走査の順序に依存してしまう（Task 4 の実装者が発見）。
  >
  > 2段の形は**構成上推移的**で、意図（「最良の中央値と、そこから有意に劣らない
  > 範囲で最も安定したもの」）をそのまま表す。**1対1の比較に戻さないこと。**
- **サンプルが5未満の候補は比較から外す。** 接続に失敗した候補や S1 で除外された
  候補には記録が無い。**どの候補も5に届かなければグループの先頭へ戻す**
  （利用者が宣言した優先順位に従う）
- 戻る先が**いまの候補と同じなら切り替えない**（無駄な切断を作らない）

### 残る限界

**候補ごとの測定時刻がずれる。** 候補A は T+0、候補F は T+6分で、そのあいだに
回線状況が変わりうる。**比較は一周の中だけで行い、一周が終わったら記録を捨てる。**
横断的に「この候補はいつも良い」を学習するのは別の話で、§5 の将来の入口に置く。

## 2-B. 一周したあとの再開（旧仕様 §4-5 の禁止を**覆す**）

旧仕様 §4-5 は「**時間による自動解除は設けない**」と書き、同じ趣旨が
`FailoverController` と `FailoverService` の KDoc、および実装計画にもある
（計4箇所）。理由は「遅いという判定は誤りうる（旧 §6）ので、誤判定のまま
時間で再武装すると候補の間を延々と行き来し続ける」であった。

### 決めたこと: 設定可能な間隔で再開できるようにする（既定は再開しない）

**前提が2つ変わったので覆す。**

**(1) 判定の根拠が変わった。** 応答時間を本体に据えたことで、旧 §6 の
誤判定1・2・4・5 が絞れる（§3）。「判定は誤りうる」という前提が弱まった。
ただし**消えてはいない**（§3 の新しい限界）。

**(2) そして、ここが最も重要である——再開は「切り替える」ことではない。**
**再開が行うのは一周の記録を消すことだけで、切替には §2 の3条件の判定が
別途必要である。** 条件が揃わなければ何も起きない。

> **したがって、状況が改善していれば再開しても静かなままである。**
> 代償を払うのは**劣化が本当に続いているとき**だけで、そのときは
> 「一周ぶんの切断を、設定した間隔ごとに繰り返す」ことになる。
> **これは利用者が間隔を決めて選ぶ性質のものである**——旧仕様が恐れた
> 「原因不明の断続的な切断」は、間隔が利用者の設定として見えていれば
> 原因不明ではない。

### 仕様

- 設定項目 `rearmAfterLapMin`（分）。**`0` は「再開しない」**を意味する
- **既定は `0`（再開しない）。** 現在の挙動を変えずに、**望む人だけが有効にする**
- 範囲は 0〜240 分、刻みは 15 分（設定画面のステッパー。既存の作法に合わせる）
- 計時の起点は**一周が止まった時刻**（§2-A の「最良へ戻す」切替が済んだ時点）
- `rearmAfterLapMin` を経過したら、そのグループの一周の記録を消す。
  **消すだけで、切替は行わない**
- **既存の3つの解除経路は据え置く**——利用者の明示的な接続、グループ構成の変更、
  本機能の設定の変更（設定変更には `rearmAfterLapMin` 自身の変更も含む）

### 裁定78 / `DECISIONS` 項目3 との関係（混同しないこと）

項目3 は「**人が居るか**」「**その指示がまだ生きているか**」を時計で判定することを
禁じている。**この再開の時計はそのどちらでもない。** 自動動作の冷却期間であり、
`connectTimeoutSec` や `graceAfterConnectSec` と同じ種類の、正当な期限である。

**将来これを見た人が項目3 違反として消さないよう、この段落を残す。**

## 3. この改訂で絞れる誤判定と、絞れないもの

旧仕様 §6 の項目に対応させる。

| 旧 §6 | 内容 | 改訂後 |
|---|---|---|
| 1 | 低ビットレート再生を「遅い」と誤判定 | **絞れる。** 経路が健全なら応答時間の条件が成立しない |
| 2 | 配信元の不調を VPN のせいにする | **絞れる。** 同上。配信元が遅くても経路の応答時間は悪化しない |
| 3 | 短時間の切替連発 | **変わらない。** 旧仕様 4-5 の「一周したら諦める」で上限が付く |
| 4 | 待機中の雑多な通信を「使っている」と誤判定 | **絞れる。** 送信側の条件を受信の下限に置き換え、さらに経路の健全性を要求する |
| 5 | 送信が主体の通信を「遅い」と誤判定 | **絞れる。** 同上。上り主体の通信は受信が下限に届かない |

### 新しく残る既知の限界（正直に記録する）

1. **遅延は良いのに帯域だけ細い回線を見落とす。** 帯域制限やシェーピングを
   受けた経路は、応答時間が健全なまま容量だけ低い。**受動観測では測れない。**
   これを捉えるには能動的な測定（トンネル経由で実際に落としてみる）が必要で、
   旧仕様の「追加の通信は行いません」と衝突する。**改訂版でも採用しない。**
   採用を検討するなら別の仕様として起こすこと
2. **宛先までの距離が応答時間に乗る。** `ProbeTarget` が遠い利用者では
   `degradedRttMs` の既定が常時成立しうる。ばらつきの条件が同時に要るので
   それだけでは発火しないが、**既定値が万人向けでないことは事実**である。
   候補ごとの基準値を学習する案は、学習期間と保存先が増えるので改訂版では
   採らない（§5 に将来の入口として残す）
3. **応答時間が悪い経路でも、利用者が見ているものは問題なく見えていることがある。**
   遅延とビットレートは別物である。**切り替える判断が利用者の体験と一致しない
   場合がある**のは旧仕様と同じく残る

## 4. 変更が要る箇所

**既存 Java は変更しない。`FailoverController` と判定器は Android に依存しない**
（既存の約束。`DECISIONS` 項目3 の周辺）。

| 箇所 | 変更 |
|---|---|
| `HealthProbe`（port） | 所要時間を返せるようにする。**既存の `probe(): Boolean` は既定実装で残し**、既存の呼び出し元とテストを無改変で通す（裁定72/93 と同じ既定値の作法） |
| `TcpHealthProbe` | 1周期で3回接続し、各回の所要時間を返す。**1回でも成功すれば到達可能**（死活の意味を変えない） |
| 判定器 | `SlowLinkDetector` を置き換えるか、応答時間の窓を足す。**窓の刈り取りと「測れないときは窓を捨てる」（裁定R20）は踏襲する** |
| 一周の記録 | 候補ごとの応答時間の記録（§2-A）と、止まった時刻（§2-B）を持たせる。**どちらもメモリ上だけ。`slowLinkLaps` と同じ寿命** |
| `FailoverService` | プローブの結果を判定器へ渡す経路を足す。**新しいシグナリング経路は作らない**——既存のティックに乗せる |
| 設定画面 | `degradedRttMs` / `degradedJitterMs` / `rxFloorKbps` / `rearmAfterLapMin` のステッパーを足し、`demandTxKbps` は消える。**ラベルを「経路品質の低下で切り替える」に改める**（「速度低下」は実態と合わない）。**項目が増えるので裁定85 の D-pad 到達性を再確認する**（節 10-1 と同じ確認） |
| 保存キー | **`slow_link_settings_v1` のまま据え置く。** `DECISIONS` 項目7 のとおりキーは永続化される値で、変えると移行が必要になる。新しい項目を足し、`demandTxKbps` は読み飛ばす（前方・後方互換） |
| 既定の有効/無効 | **既定 OFF のまま。** 改訂後も実機で確認するまで常用を勧めない |

## 4-A. 設定項目（**すべて利用者が変更できる**）

**既定値を埋め込みで固定しない。** 既定値は旧仕様 §2-2 の実測から引いたものだが、
**その実測は1台の端末・1つの宛先・1つの時間帯のものである**（§3-2 の限界）。
利用者の環境で意味を持つ値は違いうるので、**4項目すべてをステッパーで変更できる
ようにする。**

保存キーは **`slow_link_settings_v1` のまま据え置く**（`DECISIONS` 項目7）。
新しい項目を足し、消える `demandTxKbps` は読み飛ばす。`kotlinx.serialization` の
既定値があるので、**古い版が書いた値を新しい版が読んでも、その逆でも落ちない。**

| 項目 | 既定 | 範囲 / 刻み | 意味 |
|---|---|---|---|
| `degradedRttMs` | **250** ms | 50〜2000 / 50 | **接続先までの往復の遅さの上限。** 応答時間の中央値がこれを超えたら「経路が遅い」側の条件が成立する |
| `degradedJitterMs` | **150** ms | 50〜1000 / 50 | **応答時間のばらつきの上限。** 窓の中の最大と最小の差がこれを超えたら成立する |
| `rxFloorKbps` | **50** kbps | 0〜500 / 50 | **「使っている」と見なす受信速度の下限。** これを下回るあいだは判定しない。**`0` は下限なし** |
| `slowRxKbps` | **1000** kbps（据え置き） | 250〜5000 / 250 | **「遅い」と見なす受信速度の上限。** 旧仕様から変更なし |
| `rearmAfterLapMin` | **0**（再開しない） | 0〜240 / 15 | **一周して止まったあと、再開するまでの時間（分）。** `0` は再開しない |

### 各項目を動かしたときに何が起きるか（画面にも出す）

**`degradedRttMs`（往復の遅さ）**

- 実測の目安: 素の回線は **約 70 ms**、遅かった接続先は **140〜380 ms**（旧仕様 §2-2）
- **上げると**: 切り替わりにくくなる。**宛先が地理的に遠い利用者は上げる必要がある**
  （§3-2 の限界。遠いだけで常時成立しうる）
- **下げると**: 誤判定が増える。宛先が遠いだけで「経路が悪い」と判定されうる

**`degradedJitterMs`（ばらつき）**

- 実測の目安: 素の回線は **約 5 ms**、遅かった接続先は **140〜336 ms**（同）
- **上げると**: 一過性の揺れを拾わなくなるが、本当に不安定な経路も見逃す
- **下げると**: 一瞬の揺れで切り替わる。**この項目は2桁の差で分かれていた**ので、
  既定から大きく下げる理由は乏しい

**`rxFloorKbps`（使っていると見なす下限）— 待機中の誤判定を防ぐ要**

- 実測の目安: **何も見ていない待機中の受信は 0.16 kbps（中央値）**。
  旧仕様 §2-1 の対象候補は **424 kbps**
- **下げると**: **待機中の誤判定が戻る。** 2026-10-09 に実際に起きた事故
  （`docs/MANUAL-TEST.md` 節 10-5-1）がこれである。**`0` にすると、誰も見て
  いないのに切り替わりうる**
- **上げると**: 低ビットレートの再生（音声のみ等）を「使っていない」と見なし、
  本当に遅いときでも切り替えなくなる

**`rearmAfterLapMin`（再開までの時間）**

- **`0`（既定）**: 一周したら、利用者が接続し直すかグループ構成・設定が変わるまで
  速度起因の切替は止まったままになる
- **値を入れると**: その時間が経つと**一周の記録を消す**。
  **消すだけで切り替えない**——切替には §2 の3条件が別途必要なので、
  **状況が改善していれば何も起きない**
- **短くすると**: 劣化が続いているとき、その間隔ごとに一周ぶんの切断が起きる
- **長くすると**: 一度諦めたら長く諦めたままになる

### 画面に出す導出文（既存の作法に合わせる）

設定画面には既に「現在の設定では、最短 30秒・最長 90秒でダウンを検知します」
という**設定から導かれる結果**の文がある。同じ形で次を出す。

```
いまの設定では、往復が 250 ms を超え、かつばらつきが 150 ms を超える状態が
60 秒続いたときに切り替えます。
受信が 50 kbps を下回っているあいだは判定しません（待機中は切り替わりません）。
一周したあとは再開しません。
```

`rearmAfterLapMin` に値が入っているときは最後の行を次に差し替える。

```
一周したあと 60 分で再開します。再開しても、条件が揃わなければ切り替わりません。
```

- **数字は設定値から出すこと。** 文面に定数を二重に書かない（旧仕様の
  「最短 X秒・最長 Y秒」と同じ扱い）
- **「待機中は切り替わりません」を必ず出す。** 2026-10-09 の事故が
  この一文で説明される項目であり、利用者が `rxFloorKbps` を 0 にしたときは
  **この行を消すのではなく警告に差し替える**こと

### 裁定85（D-pad の到達性）

**項目が4つ増えるので、設定画面の縦の長さが伸びる。** 節 10-1 と同じ確認
（すべての項目へ D-pad で到達でき、画面外に落ちていないこと）を**実装後に
必ずやり直すこと。** 2026-10-08 の節 10-1 では最後の項目が10手目だったので、
増えたぶんだけ手数が伸びる。

## 7. テスト方針

- **判定器は純関数として JVM でテストする。** 応答時間の列を与えて判定を固定する
- **旧仕様 §2-2 の実測値を入力にしたテストを置く。** 素の回線（73.5 / mdev 5.0）で
  発火せず、遅い候補（137〜379 / mdev 140〜336）で発火すること。**実機で取った
  数字を回帰テストに固定する**のがこの改訂の要点である
- **2026-10-09 の誤判定の入力も固定する。** 受信 5 / 送信 86 kbps かつ経路健全の
  組み合わせで**発火しないこと**。これが改訂の目的そのものである
- **自己レビューで見つけた穴もテストで固定する。** 「受信も送信もほぼ0（待機中）
  だが経路の応答時間が悪い」入力で**発火しないこと**（受信の下限が効いている
  ことの確認）。この穴は改訂案の初稿に実際に存在した
- **一周後の行先をテストで固定する**（§2-A）。応答時間の記録を与えて、
  最良の候補が選ばれること／差が `degradedJitterMs` 未満ならばらつきで決まること／
  同値ならグループの順序で決まること／サンプル不足なら先頭へ戻ること／
  戻る先が現候補なら切り替えないこと
- **設定の範囲と丸めをテストで固定する**（§4-A）。各項目の上下限で張り付くこと、
  刻みどおりに動くこと、`rxFloorKbps = 0` と `rearmAfterLapMin = 0` が
  それぞれ「下限なし」「再開しない」として扱われること。
  **導出文もテストで固定する**（純関数にして、設定値から文面が出ること）
- **再開をテストで固定する**（§2-B）。`rearmAfterLapMin = 0` では永久に
  再開しないこと／経過後に一周の記録が消えること／**消えただけでは切替が
  起きないこと**（3条件の判定が別途必要であること）
- 機械生成のテスト（`FailoverControllerInvariantTest` / 性質テスト）は維持。
  I5・I6・I9・I10 は経路品質起因の切替にも同じ形で適用する。
  **I5（一周あたりメンバー数−1）は §2-A の「最良へ戻す」切替を
  予算に数えるかどうかを決めてから適用する**——数えないと予算が1回ぶん
  増えるので、**数えない**とし、その旨を I5 に書くこと
- **実機確認は `docs/MANUAL-TEST.md` 節10 を書き直す。** 10-5（待機中）は
  **この改訂の合否を決める項目**として最初に行う
